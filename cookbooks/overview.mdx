A cookbook takes one use case from an empty workspace to production. Where the
[Documentation](/v2/overview) explains each feature on its own, a cookbook
shows how the features fit together for a specific product, with code you can
copy.

## How every cookbook is laid out

Each cookbook follows the same order, so you can jump to the part you need.

| Section | What you get |
| :--- | :--- |
| **What you'll build** | The finished behaviour, in plain terms, and what you need before you start. |
| **How it works** | The moving parts and the order they talk to each other. |
| **Steps** | Numbered steps, each with complete code in cURL, Python and Node.js where it applies. |
| **Test it** | A short configuration that shows every behaviour in a few minutes, and a troubleshooting table. |
| **Privacy and compliance** | What the recipe stores, what you must tell your users, and how to keep keys and links safe. |
| **Production checklist** | What to confirm before real users arrive. |

Cookbooks link to the reference pages for every field and error code instead of
repeating them. When a cookbook and a reference page seem to disagree, the
reference page is correct — tell us at [help@miraiminds.co](mailto:help@miraiminds.co).

## Before you start

Every cookbook assumes:

- A workspace API key (`sk_live_…`), and its webhook secret (`whsec_…`) when
  the recipe receives webhooks. See the [Quickstart](/v2/quickstart).
- A backend that can keep the key secret. The key never goes to a browser or a
  mobile app.
- An HTTPS endpoint for [webhooks](/v2/webhooks), when the recipe uses them.
  While you build, a tunnel to your laptop works.

Base URL in the examples: `https://sandbox.voice.miraiminds.co`. Use the API
host your key was issued for.
