Use tools to look up customer information, check an order, book an appointment,
or send a call outcome to your CRM. You choose when each tool runs and whether
the voice agent waits for its result or keeps the conversation going.

Tools belong to an [agent](/v2/agents). Each call uses a snapshot of that
agent's configuration, so editing a tool affects new calls.

| Phase | When it runs | Use it for |
| --- | --- | --- |
| `pre_call` | Before dialing, before answering an incoming call, or before opening browser audio. A background pre-call tool starts then and answers during the call. | Fetch context, personalize the greeting, choose the voice and language, or skip a call. |
| `on_call` | When the voice agent chooses it during the conversation. | Lookups, bookings, and background requests. |
| `post_call` | After the call has settled. | Send outcomes to your CRM or schedule a follow-up. |

Pre-call and post-call tools run in the order you list them. On-call tools use
`description` and `when` to tell the voice agent when to invoke them.

<Note>
[Node-based agents](/v2/node-agents) support all three tool phases. A start or
conversation node offers only the on-call tools named in its `data.tools`,
alongside its transitions. Define those tools on the agent first, or save the
definitions and graph together. Keep **End call** disabled or absent: a flow
ends at its end nodes. See the [Node.js editor cookbook](/cookbooks/node-flow-builder).
</Note>

## Configure tools in Agent Studio

Open an agent in **Agent Studio**, then choose **Tools** in the agent navigation.
The main navigation becomes an icon rail while you work. Switch to **Prompt**
to edit the conversation without losing your tool changes.

The first tool opens automatically when you choose a phase. **Test agent** stays
visible while you edit. Type `@` in the prompt or a supported tool field to insert
available context. Variables and tool references are highlighted differently in
the prompt, and pre-call results are grouped under the tool that returned them.

1. Choose **Pre-call**, **On-call**, or **Post-call**, then click **HTTP request**.
2. Enter a unique tool name, an HTTP method, and your HTTPS endpoint. Expand
   **Headers**, **Query parameters**, or **JSON body** as needed.
3. For on-call requests, open **Inputs** to add the values the
   agent should collect. Each input has a name, type, description, and required
   setting. Reference these values in your request with `{{ args.order_id }}`.
4. Open **Behavior** to describe when an on-call tool should run and set
   conditions and failure handling. For an on-call or pre-call
   HTTP tool, choose **Wait for result** or **Run in background**. A background
   result goes back to the agent when it is ready.
5. Click **Save changes** at the top of the agent workspace. Prompt and tool
   edits save together as one agent revision.
6. Open the tool's **Test** tab, supply sample inputs, and click **Run test**.
   Inspect the status, response time, returned fields, and full receipt.

<Note>
  **Run test** executes the saved tool against your real endpoint. It does not
  place a phone call. Save your edits before testing a new version. If the agent
  changed in another editor, reload it before running the test.
</Note>

In **Response**, you can transform the result with jq. For a pre-call tool,
choose which returned fields become prompt variables. For example, selecting
`name` from `lookup_customer` makes `{{lookup_customer.name}}` available in the
prompt and `{{ vars.lookup_customer.name }}` available to later requests. A
pre-call tool's result can also
[set the call's voice and language](#set-the-voice-and-language-for-the-call).

Use **Authentication & secrets** to store a credential or select a stored
Bearer token. You can reference any stored secret in a header with
`{{ secrets.crm_api_key }}`. Secret values are never returned to the editor.

Pre-call and post-call tools run independently of the conversation's LLM. Use
**Move up** and **Move down** to arrange their order. An on-call condition is
checked against call inputs and pre-call results before the conversation
starts. During the call, the tool's **When should the agent use it?**
instructions tell the agent when to invoke it.

Supported actions such as ending a call or scheduling a callback appear under
**Add preset** for the phases they support. You can still edit nested
conditions and more complex argument schemas in the advanced JSON fields.

## Default tools

New agents created in Agent Studio include two editable tools. Existing agents
keep their current configuration. To add either tool to an existing agent,
choose its phase and use **Add preset**. Duplicating an agent copies its saved
tools, including any tools you disabled or removed.

| Tool | Phase | What it does |
| --- | --- | --- |
| Greeting & local time | Pre-call | Fetches a time-aware greeting and local date information. Defaults to `Asia/Kolkata`. |
| End call | On-call | Lets the agent finish a conversation, with confirmation enabled. |

### Greeting and local time

The greeting preset is an ordinary HTTP request you can inspect and customize.
It runs without an LLM. Open **Query parameters** to change `timezone` to an
IANA timezone such as `Europe/London` or `America/New_York`.

```bash
curl --fail-with-body --get 'https://sandbox.voice.miraiminds.co/tools/greeting' \
  --data-urlencode 'timezone=Asia/Kolkata'
```

This public clock endpoint requires no API key and receives no customer data.
`timezone` is optional and defaults to `Asia/Kolkata`. Invalid or empty timezone
names return `400` with `error.code: "invalid_timezone"`. Responses are not cached.

```json title="Example response"
{
  "greeting": "Good afternoon",
  "outro_greeting": "Have a good day",
  "date": "2026-09-23",
  "time": "14:30:00",
  "datetime": "2026-09-23T14:30:00+05:30",
  "epoch": 1790154000,
  "timezone": "Asia/Kolkata",
  "day_of_week": "Wednesday",
  "is_weekend": false,
  "period": "afternoon"
}
```

Greetings are English: **Good morning** from 05:00, **Good afternoon** from
12:00, **Good evening** from 17:00, and **Hello** from 22:00 until 05:00, all
in the selected timezone. `epoch` is Unix time in seconds; `datetime` includes
the local UTC offset. Daylight-saving changes follow the selected timezone.

The preset selects greeting, farewell, date, time, weekday, weekend, timezone,
and period fields for your prompt. Type `@` in **First message**, choose
**greeting**, then **greeting** to insert `{{ greeting.greeting }}`. For example:

```text
{{ greeting.greeting }}! How can I help you today?
```

Later HTTP tools can use `{{ vars.greeting.date }}` and the other selected
fields. The preset has a two-second timeout and continues the call if the
request fails. You can change these settings in **Behavior**. Current-time
values describe when the pre-call request ran; they do not update during the call.

### End call

End call runs directly on the voice worker during a conversation. It does not
make an HTTP request. The default requires confirmation before hanging up and
keeps the agent's **Closing message**. To configure it, choose **On-call**, then
**End call**. Testing the tool by itself does not place or end a phone call.

## Connect your first tool

Use your workspace API key and an existing agent ID. Create an agent with the
[quickstart](/v2/quickstart) if you do not have one yet.

```bash
export MIRAI_API_BASE="https://sandbox.voice.miraiminds.co"
export MIRAI_API_KEY="sk_live_YOUR_API_KEY"
export MIRAI_AGENT_ID="agt_YOUR_AGENT_ID"
```

Keep your API key on your server. The agent and tool management routes below use
`Authorization: Bearer YOUR_API_KEY`.

### 1. Define the request

Save this as `order-status.json`. Replace `https://api.example.com/orders/status`
with your public HTTPS endpoint. This example sends `{"order_id":"ORD-123"}`
and expects a JSON response such as `{"status":"shipped","eta":"Friday"}`.

```json title="order-status.json"
{
  "name": "order_status",
  "phase": "on_call",
  "execution": "sync",
  "description": "Look up the delivery status of an order.",
  "when": "Use this when the customer asks where their order is. Ask for the order ID if needed.",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": {
        "type": "string",
        "description": "The customer's order ID, such as ORD-123."
      }
    },
    "required": ["order_id"]
  },
  "request": {
    "method": "POST",
    "url": "https://api.example.com/orders/status",
    "body": { "order_id": "{{ args.order_id }}" }
  },
  "response": { "transform": "{status, eta}" },
  "timeout_ms": 8000
}
```

### 2. Save it on your agent

This creates or replaces only `order_status` and leaves the agent's other tools
as they are. The response is `200 OK` with the updated agent, including its
`tools` and `revision`.

<CodeGroup>
```bash cURL
curl --fail-with-body -X PUT \
  "$MIRAI_API_BASE/v2/agents/$MIRAI_AGENT_ID/tools/order_status" \
  -H "Authorization: Bearer $MIRAI_API_KEY" \
  -H "Content-Type: application/json" \
  --data-binary @order-status.json
```

```python Python
import json
import os
import urllib.request

base = os.environ["MIRAI_API_BASE"]
agent_id = os.environ["MIRAI_AGENT_ID"]
with open("order-status.json", "rb") as file:
    definition = file.read()
request = urllib.request.Request(
    f"{base}/v2/agents/{agent_id}/tools/order_status",
    data=definition,
    method="PUT",
    headers={
        "Authorization": f"Bearer {os.environ['MIRAI_API_KEY']}",
        "Content-Type": "application/json",
    },
)
with urllib.request.urlopen(request, timeout=30) as response:
    agent = json.load(response)
print(agent["id"], agent["revision"])
```

```javascript Node.js
import { readFile } from "node:fs/promises";

const { MIRAI_API_BASE, MIRAI_API_KEY, MIRAI_AGENT_ID } = process.env;
const response = await fetch(
  `${MIRAI_API_BASE}/v2/agents/${MIRAI_AGENT_ID}/tools/order_status`,
  {
    method: "PUT",
    headers: {
      Authorization: `Bearer ${MIRAI_API_KEY}`,
      "Content-Type": "application/json",
    },
    body: await readFile("order-status.json", "utf8"),
  },
);
const agent = await response.json();
if (!response.ok) throw new Error(JSON.stringify(agent));
console.log(agent.id, agent.revision);
```
</CodeGroup>

You can also supply `tools: [ ... ]` when creating or updating an agent.
`PATCH /v2/agents/{id}` with `tools` replaces the **entire list**; use the
single-tool route above to change one entry. Set `tools: []` to remove all tools.

### 3. Test without placing a call

```bash
curl --fail-with-body -X POST \
  "$MIRAI_API_BASE/v2/agents/$MIRAI_AGENT_ID/tools/order_status/test" \
  -H "Authorization: Bearer $MIRAI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"args":{"order_id":"ORD-123"}}'
```

A successful response looks like this:

```json
{
  "tool": "order_status",
  "phase": "on_call",
  "kind": "http",
  "tool_run_id": "trun_EXAMPLE",
  "condition": { "result": true, "failed_leaf": "" },
  "request": {
    "method": "POST",
    "url": "https://api.example.com/orders/status",
    "headers": { "Content-Type": "application/json" },
    "body": { "order_id": "ORD-123" }
  },
  "response": {
    "status": 200,
    "ms": 240,
    "body_preview": "{\"status\":\"shipped\",\"eta\":\"Friday\"}"
  },
  "transform": { "output": { "status": "shipped", "eta": "Friday" } },
  "promoted": {},
  "missing": [],
  "would": "run",
  "status": "ok"
}
```

<Warning>
The test endpoint makes a **real HTTP request** to your endpoint. Use test data
for tools that book, charge, send messages, or update records. The
`schedule_callback` builtin is an exception: testing it validates the request
and returns `would_schedule` without scheduling a call.
</Warning>

The optional test input fields are `vars`, `args`, `call`, and `analysis`.
The response shows the condition verdict, masked request, response, transformed
result, promoted values, and missing template paths. For a pre-call tool it
also shows the [`call_settings`](#set-the-voice-and-language-for-the-call) a
call would take and `warnings` for any it would skip. Check `status` as well as
HTTP status: the test route can return `200` with a failed tool receipt.

Place a new call with this agent to try the conversation. Ask about an order;
the voice agent collects the ID, invokes the tool, and uses its result.

## Synchronous and background tools

Set `execution` separately on each **on-call HTTP tool**. You can mix both modes
on one agent. Pre-call HTTP tools can run in the background too; see
[Run a slow lookup in the background](#run-a-slow-lookup-in-the-background).

| Mode | Conversation behavior | Maximum timeout |
| --- | --- | --- |
| `"sync"` — default | The voice agent waits for the tool result before continuing its response. | 30 seconds |
| `"async"` | The tool runs in the background. The voice agent can keep talking and receives the result when ready. | 300 seconds |

For example, collect another detail while a slow delivery lookup runs:

```json
{
  "name": "delivery_lookup",
  "phase": "on_call",
  "execution": "async",
  "description": "Check delivery availability for this customer.",
  "when": "Start once when the customer asks about delivery. While the lookup runs, ask for their preferred delivery day. Use the returned availability when it arrives.",
  "request": {
    "url": "https://api.example.com/delivery",
    "query": { "customer_id": "{{ vars.customer_id }}" }
  },
  "timeout_ms": 60000
}
```

Pass `customer_id` in the call's `variables`. The voice agent should acknowledge
that work is pending, keep asking useful questions, and confirm the outcome
only after receiving the final result. Do not ask it to repeat the same request
while the first one is running.

- A user interruption does not cancel an accepted background request.
- If the result arrives during the call, the voice agent can use it when ready.
- If the call ends first, the request continues and its result is available in
  [tool receipts](#inspect-tool-results). It cannot be spoken to a caller who has left.
- Late results do not rewrite a `call.completed` event already delivered. Read
  receipts for the final result; `call.processed` is not a completion signal for
  background on-call tools.
- `execution: "async"` is rejected for builtins and post-call tools. Builtins
  decide things and run in step; post-call tools already run after the
  conversation.

`speak_while` is an optional short line spoken as a tool starts, such as
`"Let me check that for you."`. If you leave it empty, the agent speaks no
canned filler. An async tool still lets the voice agent continue the
conversation.

## Before a call: fetch context or skip dialing

### Personalize the greeting

Add this tool to your agent. Suppose the endpoint returns
`{"name":"Asha","plan":"Premium"}`:

```json
{
  "name": "customer_lookup",
  "phase": "pre_call",
  "request": {
    "url": "https://api.example.com/customers/{{ vars.customer_id }}"
  },
  "response": { "select": ["name", "plan"] },
  "on_failure": "abort"
}
```

Pass `{"customer_id":"cus_42"}` in the call's `variables`. The selected fields
become `customer_lookup.name` and `customer_lookup.plan`.

Use `{{customer_lookup.name}}` in the agent's `first_message` or `system_prompt`.
Inside another tool's template, use `{{ vars.customer_lookup.name }}` instead.
The pre-call request runs before dialing, before answering an incoming call,
or before opening browser audio.

On an incoming call the caller is already ringing, so pre-call tools get about
two seconds in total. A tool still running when that time is up counts as a
timeout and follows its `on_failure` rule: with `"continue"` the call is
answered without that tool's values, and with `"abort"` it is not answered.
On incoming calls, `{{ vars.caller_number }}` and `{{ vars.called_number }}`
are available to look the caller up. Keep incoming-call lookups fast. Move
slower work to a [background pre-call tool](#run-a-slow-lookup-in-the-background),
which doesn't count against the two seconds, or to an on-call tool with
`execution: "async"` ([background tools](#synchronous-and-background-tools)).

`on_failure: "abort"` prevents the call if this lookup fails. Nothing is
dialed, or the incoming caller is not answered, and the call ends `failed`
with `ended_reason: "precall-tool-failed"`. The default, `"continue"`, lets the
call go ahead, so if you keep it, write the greeting to handle missing values.

### Set the voice and language for the call

A pre-call tool can choose the voice and the languages of the call it runs
before. Put a `call_settings` object at the top level of the tool's result. The
result is the response after `response.transform`, the same object `select`
reads, and without a transform it is the response body your endpoint sent.

If your endpoint answers:

```json
{
  "name": "Mehul",
  "call_settings": { "voice_id": "sameer", "language": "gu", "secondary_languages": ["en"] }
}
```

the call speaks in `sameer` and listens for Gujarati and English from its
first word. The keys and their rules are the same as on
[`POST /v2/calls`](/v2/calls#call-settings).

With a transform, you can turn any API's answer into call settings without
changing that API. This tool calls a public echo service and builds
`call_settings` from what it echoes back:

```json
{
  "name": "echo",
  "phase": "pre_call",
  "request": {
    "url": "https://httpbin.org/anything",
    "query": { "word": "PINEAPPLE", "voice": "sameer", "lang": "gu" }
  },
  "response": {
    "transform": "{word: .args.word, call_settings: {voice_id: .args.voice, language: .args.lang}}",
    "select": ["word"]
  }
}
```

The call runs in `sameer` and Gujarati, and `{{echo.word}}` reads `PINEAPPLE`
in the prompt. `call_settings` is not a variable itself unless `select` names
it.

- Only a pre-call HTTP tool that waits for its result and succeeds sets
  anything. A failed or skipped tool sets nothing, and a
  [background](#run-a-slow-lookup-in-the-background) tool's `call_settings`
  are ignored because it answers after the call has started.
- Tools run in order, and a later tool wins for each key it sets.
- `null` means not set, so a transform that maps a missing field leaves the
  call's value as it was.
- A value we can't use never fails the call. That covers a `call_settings`
  that is not an object, a key with the wrong type, an unknown key and a value
  that breaks the rules. The call keeps the value it had, and the tool's
  receipt says what was skipped.
- The [call object](/v2/calls#on-the-call-object) names the tool that chose
  each value, such as `"voice_id": "pre_call:echo"`.

The receipt in [`GET /v2/calls/{id}/tool_runs`](#inspect-tool-results) shows
the keys the call took in `call_settings` and anything skipped in `warnings`:

```json title="A receipt with one key skipped"
{
  "tool_run_id": "trun_01K8F2A7C9E1G3J5L7N9Q1S3U5",
  "name": "user_lookup",
  "phase": "pre_call",
  "kind": "http",
  "status": "ok",
  "http_status": 200,
  "ms": 412,
  "call_settings": { "language": "gu" },
  "warnings": [
    "call_settings.voice_id \"robot\" is not a voice; it must be one of ashu, munshi, neha, sameer, shruti, tanvi; the call keeps its current value"
  ]
}
```

[Testing the tool](#3-test-without-placing-a-call) checks its `call_settings`
against the agent the same way and returns `call_settings` and `warnings`, so
you can see what a call would take before you place one.

### Skip when a condition holds

```json
{
  "name": "skip_call",
  "phase": "pre_call",
  "condition": { "field": "vars.do_not_call", "op": "is_true" },
  "builtin": { "reason": "Customer requested no further calls" }
}
```

When the condition matches, nothing is dialed and the call is not charged. On
an incoming call, the call is not answered.
The call ends as `aborted` with `ended_reason: "skipped-by-condition"`. A
campaign contact becomes `skipped` and is not retried as a failed attempt. Use
it alongside your [workspace do-not-call list](/v2/dnc).

### Run a slow lookup in the background

Set `"execution": "async"` on a pre-call HTTP tool when the lookup is slow and
the call should not wait for it. It starts at the same moment as the other
pre-call tools, and the call is dialed, or the incoming caller answered,
without waiting for it. On an incoming call it does not count against the
two-second budget.

```json
{
  "name": "caller_history",
  "phase": "pre_call",
  "execution": "async",
  "on_failure": "continue",
  "timeout_ms": 60000,
  "request": {
    "url": "https://api.example.com/callers/history",
    "query": { "caller": "{{ vars.caller_number }}", "call_id": "{{ call.id }}" }
  },
  "response": { "select": ["last_topic", "open_ticket"] }
}
```

In Agent Studio, choose **Run in background** under the tool's **Behavior**.

When it answers:

- Its receipt is in [`GET /v2/calls/{id}/tool_runs`](#inspect-tool-results)
  with `phase: "pre_call"`, and the [live events](/v2/live-events#pre-call-tools)
  show it finishing.
- Its selected values join the call's variables. On-call tool requests can
  read them as `{{ vars.caller_history.open_ticket }}`, and so can post-call
  tools and the [analysis prompt](/v2/analysis#variables-in-the-prompt).
- If the phone or browser call is still going, the agent gets the new values
  and uses them from its next reply. It does not speak up just because they
  arrived.

A background pre-call tool answers after the call has started, which sets its
limits:

- It can't stop the call, so `on_failure` must be `"continue"`. Decide whether
  a call happens with a tool that waits, using `on_failure: "abort"` or a
  [`skip_call`](#skip-when-a-condition-holds).
- It can't set the voice or language. Its `call_settings` are ignored, and its
  receipt says so in `warnings`.
- Nothing decided before it answers may read its values. A waiting pre-call
  tool's request or condition, `skip_call`'s condition or reason, and an
  on-call tool's condition may not use `vars.<tool>.<key>` or `tools.<tool>` of
  a background tool. Saving such an agent returns `400 invalid_tools` with the
  path. An on-call tool's request and post-call tools may read them.
- It reads the call's own variables only, such as `vars.caller_number`. All
  pre-call tools start together, so the others' outputs don't exist yet.
- Its values can't fill `first_message` or `system_prompt`. Those are filled
  in before the call starts, so its placeholders there would be empty.

Its timeout can be up to 120 seconds. The default is 5 seconds, as for every
pre-call tool, so set `timeout_ms` for a slow lookup. A tool that fails or runs
out of time leaves its receipt and nothing else.

If the call ends before the tool answers, the agent never hears the values.
They are still saved with the call, but post-call tools and analysis that
started before the answer arrived run without them. A `skip_call` or an
`abort` that stops the call before it starts also cancels the background
tool.

## Conditions and templates

`condition` decides whether a tool is available or runs. `when` is a
natural-language instruction that tells the voice agent when to choose an
on-call tool.

```json
{
  "all": [
    { "field": "vars.customer_id", "op": "exists" },
    { "field": "vars.do_not_call", "op": "is_false" }
  ]
}
```

Combine conditions with `all`, `any`, and `not`. Supported operators are:

| Operators | Meaning |
| --- | --- |
| `eq`, `neq` | Equality or inequality. |
| `contains`, `not_contains`, `starts_with`, `ends_with` | Case-insensitive text comparisons. |
| `gt`, `gte`, `lt`, `lte` | Numeric comparisons, or lexical comparisons for nonnumeric values. |
| `in`, `not_in` | Membership in the supplied `value` array. |
| `exists`, `not_exists` | Present and nonempty, or absent/empty. |
| `is_true`, `is_false` | Recognizes `true/1/yes/on` and `false/0/no/off`. |
| `matches` | RE2 regular expression, at most 200 characters. |

Conditions support up to eight nested levels and 64 comparisons. Use `exists`
or `not_exists` when checking for a missing value.

Pre-call and post-call conditions are evaluated before each tool runs. The set
of available on-call tools is chosen when the call is prepared, after pre-call
outputs exist, so base an on-call condition on call inputs and pre-call
results. Finishing one on-call tool does not make new tools available, and
model arguments are not available when the initial tool list is chosen.

### Values you can reference

| Namespace | Available values |
| --- | --- |
| `vars.*` | Call input values and promoted pre-call outputs. |
| `call.*` | Call identifiers, `to`, `from`, `direction`, tier, and status; final duration and outcome after the call. On an incoming call, `call.from` is the caller's number. |
| `now.*` | Date, time, weekday, greeting, and timezone. Uses the call's timezone, defaulting to `Asia/Kolkata`. |
| `tools.<name>.*` | Results from earlier tools in the same pre-call or post-call phase. |
| `args.*` | Model-supplied arguments for an on-call request. |
| `analysis.*` | Post-call `status`, `summary`, `success`, and `data.*` when analysis is enabled, and `template.*` when the agent has [analysis templates](/v2/analysis#send-the-message-from-a-post-call-tool). |
| `secrets.*` | Stored workspace secrets, in request templates only. Never in conditions. |

Write `{{ vars.customer_id }}` to insert text. Inside `request.body`, an entire
value such as `"{{= args.quantity }}"` preserves its JSON type instead of
converting it to a string. A missing text value renders empty and is listed
in the receipt; a missing typed value becomes `null`.

Filters are `default:"value"`, `json`, and `urlencode`, for example
`{{ vars.customer_name | default:"there" }}`. Use `request.query` for query
parameters; values are URL-encoded automatically.

Test a condition without calling an external endpoint:

```bash
curl --fail-with-body -X POST \
  "$MIRAI_API_BASE/v2/agents/$MIRAI_AGENT_ID/conditions/test" \
  -H "Authorization: Bearer $MIRAI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "condition":{"field":"vars.do_not_call","op":"is_true"},
    "scope":{"vars":{"do_not_call":"true"}}
  }'
```

## Store credentials as workspace secrets

Store a secret before saving a tool that references it:

```bash
curl --fail-with-body -X PUT "$MIRAI_API_BASE/v2/secrets/crm_key" \
  -H "Authorization: Bearer $MIRAI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"value":"YOUR_CRM_API_KEY"}'
```

Reference its name in your tool's request headers:

```json
{
  "Authorization": "Bearer {{ secrets.crm_key }}"
}
```

Secrets are scoped to your workspace, encrypted at rest, and write-only.
`GET /v2/secrets` returns names and timestamps, never values. Requests and
results shown in receipts mask resolved secret values. Keep credentials out of
prompts, call variables, and literal tool definitions.

To rotate a credential, `PUT` the new value to the same secret name. To delete
it, remove references from your agents first, then call
`DELETE /v2/secrets/crm_key`; a referenced secret returns `409`.

## After a call: send the outcome to your CRM

```json
{
  "name": "crm_update",
  "phase": "post_call",
  "request": {
    "method": "POST",
    "url": "https://api.example.com/call-outcomes",
    "headers": { "Authorization": "Bearer {{ secrets.crm_key }}" },
    "body": {
      "call_id": "{{ call.id }}",
      "status": "{{ call.status }}",
      "duration_seconds": "{{= call.duration_secs }}"
    }
  },
  "retry": { "attempts": 2, "backoff_ms": 500 }
}
```

Post-call tools run after settlement. Their failure does not change call status
or billing. If your agent has [analysis](/v2/analysis) enabled, a post-call tool can also read
`analysis.summary`, `analysis.success`, `analysis.data.*` and, with templates,
`analysis.template.*`. Use a condition on
`analysis.status` or `analysis.success` when the request requires a successful
analysis result.

### Send the whole call with Send webhook

The `webhook` tool posts the finished call to an HTTPS URL you own. You do not
write a request body. We build it, and it carries the whole record: the call's
details, the transcript, your after-call results, and whether a recording was
stored.

It runs once after every call the agent handles. That includes inbound calls to
your numbers, outbound calls, browser calls, text chats, campaign calls,
WhatsApp calls, and scheduled callbacks.

In Agent Studio, open **Tools**, choose **Post-call**, click **Add preset**,
and pick **Send webhook**. Enter your URL and save. Over the API, add this tool
to the agent:

```json
{
  "name": "webhook",
  "phase": "post_call",
  "builtin": { "url": "https://api.example.com/calls/finished" }
}
```

`url` is the only setting. There is no `events` setting: the tool sends one
request per call. If an agent you saved earlier still has `builtin.events`, we
accept it and ignore it.

Your server receives a `POST` like this one, for an inbound call:

```json title="Body sent to builtin.url"
{
  "call": {
    "id": "call_01K8INB4M8N3P6R2S5T7V9W1YA",
    "object": "call",
    "agent_id": "agt_01K7Q9F3K7M2N5P9R4T6V8W0XZ",
    "agent_revision": 3,
    "channel": "phone",
    "route": "trunk",
    "direction": "inbound",
    "from": "+919876543210",
    "to": "+919876543211",
    "phone_number_id": "pn_01K8D2H5J7L9N1Q3S5U7W9Y1AC",
    "provider": "plivo",
    "tier": "t3",
    "status": "completed",
    "ended_reason": "customer-ended-call",
    "started_at": "2026-10-12T05:23:07Z",
    "ended_at": "2026-10-12T05:24:12Z",

    "summary": "The caller moved their appointment to Friday at 4 pm.",
    "success": true,
    "data": { "outcome": "rescheduled", "slot": "2026-10-16T16:00:00+05:30" }
  },
  "transcript": {
    "status": "ready",
    "turns": [
      { "role": "assistant", "text": "Namaste, Sunrise Clinic. How can I help you?", "start_ms": 0, "end_ms": 2900 },
      { "role": "user", "text": "I want to move my appointment to Friday.", "start_ms": 3400, "end_ms": 6100 },
      { "role": "assistant", "text": "Done. Friday at 4 pm with Dr. Rao. Anything else?", "start_ms": 6600, "end_ms": 10200 },
      { "role": "user", "text": "No, thank you.", "start_ms": 10700, "end_ms": null }

  "tool": "webhook"

```

| Field | Meaning |
| --- | --- |
| `call.id`, `call.agent_id`, `call.agent_revision` | The call, the agent, and the agent revision the call used. |
| `call.channel`, `call.route`, `call.direction` | How the call ran: `phone`, `web`, `text` or `realtime`; the route; `inbound` or `outbound`. `route` can be empty on calls that use no phone line. |
| `call.from`, `call.to` | The numbers. On an inbound call, `from` is the caller and `to` is your number. Empty on calls with no number. |
| `call.phone_number_id`, `call.provider` | Your number and its telephony provider. `phone_number_id` is empty, and `provider` is absent, when the call used none. |
| `call.status`, `call.ended_reason` | The [final status](/v2/calls#statuses) and why the call ended. |
| `call.started_at`, `call.ended_at`, `call.duration_secs` | When the conversation started and ended, in UTC. `started_at` is an empty string if the call never connected. |
| `call.answered`, `call.user_spoke`, `call.turns` | Whether the call connected, whether the other person said anything, and how many turns each side took. |
| `call.cost` | What the call cost. `paise` and `amount_inr` are the same amount. `per_min_inr` and `billing_block_secs` are the rate it was billed at. It can also carry the other `cost` fields of the [call object](/v2/calls#the-call-object). |
| `call.metadata` | The `metadata` you set when you created the call. `{}` when there is none. |
| `call.test` | `true` for a test call or a **Run test** request. |
| `call.transcript_status` | `ready`, `empty` or `failed`. The same value [`GET /v2/calls/{id}`](/v2/calls#get-a-call) reports. |
| `call.campaign_id`, `call.contact_id`, `call.parent_call_id`, `call.skip_reason` | Set on campaign calls, scheduled callbacks and skipped calls. Empty strings otherwise. |
| `call.flow` | Only on a [node-based agent's](/v2/node-agents) call: the [flow outcome](/v2/calls#flow-outcome). |
| `call.tool_runs` | Only when the call ran tools before or during the conversation: one short receipt per tool, the same shape as `data.call.tool_runs` on webhook events. |
| `analysis` | Your after-call results. `status` is `done`, `failed`, `skipped` or `not_enabled`. `summary` is always present. `success` and `data` are present when the analysis produced them. |
| `transcript.status` | `ready`, `empty`, `failed` or `fetch_required`. See the next table. |
| `transcript.turns` | The turns when `status` is `ready`, in the same shape as [`GET /v2/calls/{id}/transcript`](/v2/calls#get-the-transcript). `[]` otherwise. |
| `recording.status` | `available`, `disabled` or `not_available`. See below. |
| `tool` | The tool's name, `webhook`. |

Two more fields appear inside `call` on some calls. `calls_from_source` says
how an outbound phone call's number was chosen: `request`, `agent`, `shared` or
`trunk`. `identity` holds the caller's WhatsApp identity on a WhatsApp call. We
may add fields. Ignore the ones you do not use.

| `transcript.status` | Meaning |
| --- | --- |
| `ready` | The turns are inline. |
| `empty` | Nobody spoke, or the call never connected. |
| `failed` | No transcript reached us in time. The request is still sent. |
| `fetch_required` | The transcript is larger than 512 KB, so `turns` is empty. Fetch it with [`GET /v2/calls/{id}/transcript`](/v2/calls#get-the-transcript). We never cut a transcript short. |

| `recording.status` | Meaning |
| --- | --- |
| `available` | Audio was stored. Fetch it with [`GET /v2/calls/{id}/recording`](/v2/calls#get-the-recording) and your API key. |
| `disabled` | Recording was turned off for this call. |
| `not_available` | No audio was stored when we sent the request. A text chat or a call that never connected has none. |

The body does not contain a recording link. Ask for one when you need the
audio: `GET /v2/calls/{id}/recording` redirects to a link that expires.

**When it is sent.** After the call ends, we wait for two things and then send:

- The transcript. It is usually stored before the call ends, so there is no
  wait. If it is late, we wait until 2 minutes after the call ended. After
  that we send the request with `transcript.status` set to `failed`.
- Your after-call results, if the agent has analysis turned on. We wait until
  they are ready, for up to 7 minutes. After that we send the request with
  `analysis.status` set to `failed`.

We never hold the request back because one part is missing. The terminal
event, such as `call.completed`, does not wait for any of this. Use it to know
the call ended. Use this request to process the conversation.

**Signature.** The request carries `X-Mirai-Signature`, signed with your
workspace's webhook secret over the raw body. It is the same header and the
same check as for call events. See
[signature verification](/v2/webhooks#signature-verification). Verify against
the bytes you received, before you parse them.

**Delivery.** Any `2xx` reply counts as delivered. We try up to three times by
default, 15 seconds each. Change that with `timeout_ms` and `retry` on the
tool. A `4xx` reply is not retried. Each request has `X-Mirai-Call-Id`,
`X-Mirai-Tool-Run-Id` and `X-Mirai-Attempt` headers. Retries of the same
request keep the same `X-Mirai-Tool-Run-Id`, so deduplicate on it.

**Size.** Most bodies are a few kilobytes. A very long call can reach about
600 KB, so make sure your server accepts a body that large. The 256 KB request
limit applies to bodies you write yourself, not to this one.

**Test it.** Open the tool's **Test** tab and click **Run test**. We send a
sample call in exactly this shape: `call.test` is `true`, the transcript has
four sample turns, the cost is zero, and `recording.status` is
`not_available`. A test request is not signed, so it has no
`X-Mirai-Signature` header.

A [post-call rerun](#rerun-post-call-tools) sends the whole body again with a
new `X-Mirai-Tool-Run-Id`.

### Receive `call.processed`

The terminal event, such as `call.completed`, describes the finished call.
`call.processed` reports the subsequent analysis and post-call tool results. It
is emitted when the agent has post-call tools or analysis enabled, unless you
set `emit_processed_webhook: false` on the agent. That setting turns off only
the event. Analysis and post-call tools still run.

The event uses your call's `webhook_url` and the normal
[webhook signature verification](/v2/webhooks#signature-verification).
Alongside `data.call`, it includes:

```json title="Processing portion of a call.processed event"
{
  "processing": {
    "analysis": "not_enabled",
    "post_call_tools": "done",
    "version": 1
  }
}
```

This object is at `data.processing`. `post_call_tools` is `done`, `partial`,
`failed`, or `none`; `analysis` is `done`, `failed`, `skipped`, or `not_enabled`.
A tool skipped by its condition is not a processing failure. Webhook retries
can change delivery order, so handle events by their type and processing version.

### Rerun post-call tools

```bash
curl --fail-with-body -X POST \
  "$MIRAI_API_BASE/v2/calls/call_YOUR_CALL_ID/post_call/rerun" \
  -H "Authorization: Bearer $MIRAI_API_KEY"
```

```json
{ "call_id": "call_YOUR_CALL_ID", "status": "processing", "version": 2 }
```

A rerun uses the call's saved agent configuration, creates new tool-run IDs,
and emits a new `call.processed` version. It does not rewrite the earlier event.
It returns `409` if the call has not finished or processing is already running.

<Warning>
An explicit rerun repeats external actions. For requests that update records or
create bookings, deduplicate retries using the `X-Mirai-Tool-Run-Id` header.
The same logical retry keeps this ID; an explicit rerun gets a new one. Network
failures can leave an external action's outcome uncertain, so do not assume
exactly-once delivery.
</Warning>

## Schedule a callback

Add this minimal builtin to let the voice agent arrange a later call:

```json
{ "name": "schedule_callback", "phase": "on_call" }
```

The tool automatically exposes a required `at` argument and optional `note` to
the model. `at` should be a future RFC3339 timestamp with a UTC offset, such as
`2026-10-01T15:00:00+05:30`. Ask the customer to clarify an ambiguous time.
If you supply a custom `description` or `parameters`, we keep them.

The default window is at least 30 minutes and at most 14 days ahead. Change it
with `builtin.min_delay_minutes` and `builtin.max_days`. For a post-call
callback, configure `builtin.at` and optionally `builtin.note` as templates.

The new call targets the same person at the same tier and uses ordinary call
admission and billing. It carries `parent_call_id` and a `callback_note` input.
A scheduled callback can fail if the agent is no longer available or the
workspace cannot place the call at that time.

The tool result includes a `callback_id`. Cancel before dialing:

```bash
curl --fail-with-body -X DELETE \
  "$MIRAI_API_BASE/v2/callbacks/cbk_YOUR_CALLBACK_ID" \
  -H "Authorization: Bearer $MIRAI_API_KEY"
```

Cancellation succeeds only while the callback is pending or scheduled. Once
it has been claimed for dialing, or was already canceled, the route returns
`404`. Schedule callbacks only with the customer's agreement and observe your
[calling-window and consent requirements](/v2/limits#calling-window).

## Inspect tool results

```bash
curl --fail-with-body \
  "$MIRAI_API_BASE/v2/calls/call_YOUR_CALL_ID/tool_runs" \
  -H "Authorization: Bearer $MIRAI_API_KEY"
```

The `data` array contains receipts with the tool name, phase, status,
`tool_run_id`, start/end times, duration in milliseconds, HTTP status, transformed
result, and any error. Receipts can also include the condition verdict, masked
request, missing paths, and warnings. A pre-call receipt also has the
[`call_settings`](#set-the-voice-and-language-for-the-call) the call took from
that tool. Read these when a tool was skipped, timed out, returned an
unexpected result, or finished after hangup.

Use `GET /v2/tools/catalog` to discover supported tools, available phases,
execution modes, limits, and whether your configured model accepts structured
tool arguments. Builtins currently include:

| Name | Phase | Purpose |
| --- | --- | --- |
| `skip_call` | `pre_call` | Prevent dialing when a condition holds. |
| `end_call` | `on_call` | End the conversation. |
| `schedule_callback` | `on_call`, `post_call` | Arrange a later call. |
| `webhook` | `post_call` | Send the whole finished call to the HTTPS URL in `builtin.url`: details, transcript, after-call results and recording status. See [Send the whole call with Send webhook](#send-the-whole-call-with-send-webhook). |

An explicit `end_call` tool can use `builtin.enabled`, `builtin.message`, and
`builtin.confirm` to override the agent's [ending settings](/v2/agents#ending-a-call).
Its tool-level `enabled` and `condition` also control whether it is available.

`transfer_call` and `send_dtmf` are listed as unavailable. Saving an unavailable
builtin returns `tool_unavailable`.

## Tool definition reference

| Field | Required | Meaning |
| --- | --- | --- |
| `name` | Yes | Unique per agent; 2–40 characters matching `[a-z][a-z0-9_]{1,39}`. |
| `phase` | Yes | `pre_call`, `on_call`, or `post_call`. |
| `kind` | No | `http` or `builtin`; inferred from the definition. |
| `enabled` | No | Defaults to `true`. Set `false` to keep a tool configured but inactive. |
| `condition` | No | Condition object; omitted or `null` means no condition. |
| `description` | No | What an on-call tool does; up to 500 characters. |
| `when` | No | When the voice agent should invoke an on-call tool; up to 1,000 characters. |
| `parameters` | No | JSON Schema for model arguments; on-call only. Requires a model with native tool calling. |
| `execution` | No | `sync` by default; `async` is available for on-call and pre-call HTTP tools. |
| `speak_while` | No | Optional on-call filler line, up to 300 characters. Empty by default. |
| `request` | For HTTP | Required `url`; optional `method` (default `GET`), `headers`, `query`, and `body`. |
| `response` | No | Optional jq `transform`, `select` keys to promote, and `strict` (default `false`). |
| `timeout_ms` | No | Per-attempt timeout; at least 100 ms. See phase limits below. |
| `retry` | No | `attempts` and optional `backoff_ms` (default 500; maximum 10,000). |
| `on_failure` | No | `continue` by default. `abort` is accepted only for pre-call tools that wait for their result. |
| `builtin` | Depends on builtin | Builtin configuration, such as a skip reason or callback window. |

Requests support `GET`, `POST`, `PUT`, `PATCH`, and `DELETE`. GET and DELETE
requests cannot carry a body. If a POST, PUT, or PATCH tool omits its body,
the model's arguments become the body. Do not set transport-owned headers
`Host`, `Content-Length`, `Transfer-Encoding`, or `Connection`.

Responses with non-2xx status fail. JSON is parsed automatically; non-JSON
becomes `{"text":"..."}` unless `response.strict` is `true`. A jq transform
selects the result returned to the voice agent. `response.select` promotes
fields for use by later lifecycle steps; it does not replace `transform` for
narrowing the result the voice agent receives.

### Limits and retries

| Limit | Pre-call sync | Pre-call async | On-call sync | On-call async | Post-call |
| --- | --- | --- | --- | --- | --- |
| Default timeout | 5 s | 5 s | 10 s | 10 s | 15 s |
| Maximum timeout | 15 s | 120 s | 30 s | 300 s | 60 s |
| Default retries | 0 | 0 | 0 | 0 | 2 |
| Maximum retries | 2 | 2 | 0 | 0 | 5 |
| Maximum tools | 10 total across both pre-call modes | Shared with sync | 20 total across both on-call modes | Shared with sync | 10 |

You can define up to 40 tools per agent. On-call execution is limited to
40 runs per call and four concurrent requests per call. The pre-call phase has
a 30-second total budget, and about two seconds on an incoming call; background
pre-call tools are outside both. The post-call tool phase has a five-minute
budget, separate from any wait for analysis.

- Endpoints must use public HTTPS on port 443. Private-network destinations and
  redirects are refused.
- Request and response bodies are limited to 256 KB; URLs to 2,048 characters;
  headers and query entries to 20 each. The body the `webhook` tool builds is
  not limited to 256 KB.
- jq transforms have a 100 ms budget and 64 KB output limit. Up to 16 selected
  fields can be promoted, each with a maximum value length of 512 characters.
- Retries apply to timeouts, connection failures, and server errors. Client
  errors, blocked destinations, and transform failures are not retried.
- Tool executions currently have no separate charge. Calls and callbacks use
  the normal [call pricing](/general/tiers); your API provider may charge separately.

### Validation and runtime errors

Invalid tool definitions return `400` with a list of field errors. This shape
differs from the API's usual error envelope:

```json
{
  "error": "invalid_tools",
  "details": [
    {
      "path": "tools[0].on_failure",
      "message": "must be \"continue\" on an async pre_call tool: it finishes after the call has started, so it can no longer stop it"
    }
  ]
}
```

`error` can also be `tool_unavailable` or `tool_style_unsupported`. Fix the
listed fields before retrying. On a node-based agent, invalid node tool
references or an enabled `end_call` tool use the same shape with
`error: "invalid_flow"`; see
[node-based agent errors](/v2/node-agents#errors). Ordinary authentication, lookup, and conflict
errors keep the [standard error shape](/v2/errors).

At runtime, inspect the receipt for errors such as `timeout`, `http_429`,
`http_500`, `egress_denied`, `redirect_refused`, `transform_failed`,
`response_too_large`, `rate_limited`, or `budget_exhausted`. An on-call tool
failure is returned to the voice agent so it can explain the problem and
continue the conversation.
