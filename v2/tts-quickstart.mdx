This is the voice our agents use, offered as a standalone API. It speaks
OpenAI's `POST /v1/audio/speech` protocol, so every OpenAI SDK and every
framework with an OpenAI TTS integration can already call it. You change the
base URL and the model name, and the rest of your code stays as it is.

To hear the voices and see how the model scores, read the
[Mira TTS model page](https://voice.miraiminds.co/models/text-to-speech). To see
how its price compares with other Hindi TTS APIs, read our
[Hindi TTS API comparison](https://voice.miraiminds.co/guides/hindi-tts-api-comparison).

## 1. Get a key

Open the [console](https://sandbox.voice.miraiminds.co), go to **Developers**
and press **Create key**. You do not need an access code. The first time, the
console asks for your work email and sends you a confirmation link; open it,
then press **Create key** again. The key is a `sk_live_` secret, and the
console shows it only once. We store only its hash, so we cannot
recover a lost key; you rotate it instead. The same key works for TTS and the
rest of the [v2 API](/v2/overview), and draws on the same [wallet](/v2/wallet).

## 2. One request

```bash
curl https://sandbox.voice.miraiminds.co/v1/audio/speech \
  -H "Authorization: Bearer $MIRA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "mira-tts",
    "voice": "ashu",
    "response_format": "wav",
    "input": "नमस्ते, मैं आशु बोल रहा हूं। आपका ऑर्डर तैयार है।"
  }' \
  --output speech.wav
```

The response body is the audio itself. Keep `--output`: without it, curl
prints 300 KB of binary into your terminal and you have to reset it. If
`speech.wav` plays, the integration works, and the sections below refine it.

### Output formats

Pick the format and sample rate your player or phone line uses, and we convert
on our side as the audio streams:

| `response_format` | You get | Streams? |
| :--- | :--- | :--- |
| `pcm` | Raw signed 16-bit little-endian mono, no header. | Yes. The first bytes arrive while the rest is still being synthesised. |
| `mulaw` (also `ulaw`, `pcm_mulaw`) | Raw G.711 μ-law, 1 byte per sample. What most phone lines carry. | Yes |
| `alaw` (also `pcm_alaw`) | Raw G.711 A-law, 1 byte per sample. | Yes |
| `wav` | A playable file: 16-bit mono PCM with a WAV header. | No. It arrives in one piece once synthesis finishes. |
| `mp3` | MP3 (`audio/mpeg`). | Yes |
| `opus` | Opus in an Ogg container (`audio/ogg`). | Yes |
| `aac` | AAC in ADTS frames (`audio/aac`). | Yes |
| `flac` | FLAC (`audio/flac`), lossless. | Yes |

Send the rate in `sample_rate`, or use a value with the rate built in:

| Field | Values | Default |
| :--- | :--- | :--- |
| `sample_rate` | `8000`, `16000`, `22050`, `24000`, `44100` or `48000`. μ-law and A-law come at `8000` or `16000` only. `opus` comes at `8000`, `16000`, `24000` or `48000` only. | `48000`, except `8000` for μ-law and A-law |
| `bitrate` | `32`, `48`, `64`, `96`, `128`, `160` or `192` (kbps). A string such as `"128k"` also works. Only for `mp3`, `opus` and `aac`; with any other format it returns a 400. Low sample rates carry less: MP3 tops out at 160 below 32 kHz and at 64 below 16 kHz, and AAC at about 6 kbps per kHz (48 at 8 kHz, 96 at 16 kHz). Asking for more returns a 400 that names the most you can have. | `128`, or the most the codec carries at a lower sample rate |
| `response_format` with a rate | `pcm_8000`, `pcm_16000`, `pcm_22050`, `pcm_24000`, `pcm_44100`, `pcm_48000`, `ulaw_8000` (or `mulaw_8000`), `ulaw_16000` (or `mulaw_16000`), `alaw_8000`, `alaw_16000`, and for compressed audio `mp3_44100_128`, `opus_48000_64` and the other `mp3_<rate>_<kbps>` and `opus_<rate>_<kbps>` combinations | |

If `response_format` includes a rate, leave `sample_rate` out or send the same
value; a different one returns a 400. For a WAV at another rate, send `wav`
with `sample_rate`, for example `"sample_rate": 16000`. Values are not case
sensitive.

Any other value returns a 400 whose message lists the values we accept.
OpenAI's default format, `mp3`, works here. If you omit `response_format` you
still get `pcm` at 48 kHz, so send it explicitly.

Compressed formats are for HTTP requests. The
[WebSocket endpoint](/v2/tts-websocket) streams `pcm`, μ-law and A-law only. If
our server cannot encode a compressed format, the request returns
`503 format_unavailable` and nothing is charged. `GET /v1/models` lists the
compressed formats only when they are available.

```bash title="Phone-ready audio: 8 kHz μ-law"
curl https://sandbox.voice.miraiminds.co/v1/audio/speech \
  -H "Authorization: Bearer $MIRA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "mira-tts",
    "voice": "neha",
    "response_format": "ulaw_8000",
    "input": "नमस्ते, आपका ऑर्डर कल तक पहुँच जाएगा।"
  }' \
  --output speech.ulaw
```

Play it with `ffplay -f mulaw -ar 8000 speech.ulaw`.

```bash title="Compressed audio: MP3 at 64 kbps"
curl https://sandbox.voice.miraiminds.co/v1/audio/speech \
  -H "Authorization: Bearer $MIRA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "mira-tts",
    "voice": "shruti",
    "response_format": "mp3",
    "bitrate": 64,
    "input": "नमस्ते, आपका ऑर्डर कल तक पहुँच जाएगा।"
  }' \
  --output speech.mp3
```

`"response_format": "mp3_44100_64"` asks for the same thing in one field.

### Speed, pitch and loudness

Three optional fields change how the voice sounds. All three work on
`/v1/audio/speech` and `/v2/tts`, and on the
[WebSocket endpoint](/v2/tts-websocket#session-update).

| Field | Range | Default | Notes |
| :--- | :--- | :--- | :--- |
| `speed` | `0.5` to `2.0` | `1.0` | `pace` is accepted as another name for it. If you send both with different values, you get a 400. |
| `pitch` | `-6` to `+6` semitones | `0` | Negative is lower, positive is higher. |
| `loudness` | `0.5` to `2.0` | `1.0` | A linear gain. A soft limiter keeps loud audio from clipping. |

```bash
curl https://sandbox.voice.miraiminds.co/v1/audio/speech \
  -H "Authorization: Bearer $MIRA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "mira-tts",
    "voice": "neha",
    "response_format": "wav",
    "speed": 0.9,
    "pitch": -1,
    "loudness": 1.2,
    "input": "आपका ऑर्डर कल तक पहुँच जाएगा।"
  }' \
  --output speech.wav
```

A value outside its range, or one that is not a number, returns a 400 that
names the range. If you leave all three out, the audio is the same as before
these fields existed.

<Note>
`sample_rate` used to be ignored. If your code already sends it, check the
value: a supported rate such as `16000` now gets you audio at that rate
instead of 48 kHz, and an unsupported one such as `32000` returns a 400 that
lists the allowed rates.
</Note>

`model` is `mira-tts`. Any other value returns a `404`; older names that still
work are listed under [Compatibility](/v2/speech-compatibility#other-model-names).

### Pick a voice

```bash
curl https://sandbox.voice.miraiminds.co/v2/voices \
  -H "Authorization: Bearer $MIRA_API_KEY"
```

The voices today are `ashu`, `neha`, `shruti`, `sameer`, `munshi` and `tanvi`.
`ashu`, `neha`, `shruti` and `sameer` are Hindi voices that code-switch into
English the way real Indian speech does. `munshi` and `tanvi` speak Hindi,
English, Gujarati, Tamil and Telugu. `shruti` is the default if you omit
`voice`. Each entry gives the `voice_id`, the voice's
name and its language. To hear a voice before you choose, use the voice picker
in the console's Agent Studio. An unknown voice returns a 400 that names the
allowed set; we never swap in another voice silently. Your own
[custom voices](/v2/custom-voices) work here too: send a voice's `id`
(`cv_…`) as `voice`. The price is the same as for a built-in voice. Gujarati, Tamil and
Telugu are live too: send the text in its own script and the same voices read
it, with no language parameter. Kannada, Malayalam and Bengali work the same
way, in beta, on all six voices. Marathi is in beta too and needs one field;
see [Marathi](#marathi) below. The [language roadmap](/v2/tts-languages) has
the details.

### Marathi

Marathi is written in Devanagari, like Hindi, so its script alone doesn't say
which one it is. Its words do: a line with Marathi words such as आहे, नाही or
तुमच्या is read as Marathi without anything extra. A very short line with no
Marathi word in it ("धन्यवाद") is read as Hindi. Add `"language": "mr"` to make
every line Marathi:

```bash
curl https://sandbox.voice.miraiminds.co/v1/audio/speech \
  -H "Authorization: Bearer $MIRA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "mira-tts",
    "voice": "shruti",
    "language": "mr",
    "response_format": "wav",
    "input": "नमस्कार, मी मीरा बोलतेय. तुमची गाडी service साठी due आहे."
  }' \
  --output marathi.wav
```

`language` is optional, and today it matters only for Devanagari: `mr` makes a
line Marathi and `hi` keeps it Hindi. It also takes `mr-IN` or `Marathi`. Every
other language is read from its script, so a `language` that disagrees with
the text is ignored: Hindi text sent with `"language": "kn"` is still read as
Hindi. A value we don't recognise is ignored too, and never fails the request.
With the OpenAI SDK, pass it as `extra_body={"language": "mr"}`. The
[streaming socket](/v2/tts-websocket) has no `language` field yet, so there
Marathi is recognised by its words alone, sentence by sentence.

### What comes back

Every `200` carries its own accounting in headers, so you can meter spend and
pin a build without a second request:

| Header | Meaning |
| :--- | :--- |
| `X-Request-Id` | This request's id (`tts_…`). It identifies the row in your [request log](#your-request-log) and is the `reference` on the [ledger row](#billing). |
| `X-Chars-Billed` | Characters counted for billing. |
| `X-Cost-Paise` | What this request costs, in paise, once it completes. |
| `X-Sample-Rate` | The sample rate of the audio you received, for example `8000` or `48000`. |
| `X-Audio-Encoding` | How the samples are encoded: `pcm_s16le` (for `pcm` and `wav`), `mulaw`, `alaw`, `mp3`, `opus`, `aac` or `flac`. |
| `X-Audio-Bitrate` | The bitrate in kbps. Sent for `mp3`, `opus` and `aac` only. |
| `Content-Type` | `audio/pcm` for `pcm` at any rate, `audio/wav`, `audio/PCMU;rate=8000` for μ-law or `audio/PCMA;rate=8000` for A-law (with `16000` at 16 kHz), `audio/mpeg`, `audio/ogg`, `audio/aac` or `audio/flac`. |
| `X-Mira-Model` | The build that produced the audio, for example `miraiminds/mira-tts-v53`. Pin it when you compare quality across releases. |

Read `X-Sample-Rate` and `X-Audio-Encoding` before you play the audio. Raw
audio has no header, so playing μ-law as PCM, or 8 kHz audio as 48 kHz, gives
you noise or audio at the wrong speed.

Every error after authentication also carries `X-Request-Id`, so you can trace
a failure the same way as a success. Quote the id when you ask us about a
failed request.

## 3. Stream it

`pcm`, μ-law, A-law and the compressed formats stream: the first bytes arrive while the rest is still
being synthesised. With the OpenAI SDK, read them as they come:

```python
from openai import OpenAI

client = OpenAI(
    api_key="sk_live_...",
    base_url="https://sandbox.voice.miraiminds.co/v1",
)

with client.audio.speech.with_streaming_response.create(
    model="mira-tts",
    voice="ashu",
    response_format="pcm",
    input="चलिए numbers से start करते हैं।",
) as response:
    for chunk in response.iter_bytes():
        ...  # raw s16le mono @ 48 kHz — feed your player as it arrives
```

`sample_rate` is not an OpenAI parameter. To get another rate through the SDK,
pass it in `extra_body={"sample_rate": 16000}`.

To save the stream as a playable file, write the PCM into a WAV with Python's
own `wave` module. You need no other audio package:

```python
import os
import wave

from openai import OpenAI

client = OpenAI(
    api_key=os.environ["MIRA_API_KEY"],
    base_url="https://sandbox.voice.miraiminds.co/v1",
)

with wave.open("speech.wav", "wb") as wav:
    wav.setparams((1, 2, 48000, 0, "NONE", "NONE"))  # mono, 16-bit, 48 kHz
    with client.audio.speech.with_streaming_response.create(
        model="mira-tts", voice="neha",
        input="नमस्ते, आपका ऑर्डर कल तक पहुँच जाएगा।",
        response_format="pcm",
    ) as speech:
        for chunk in speech.iter_bytes():
            wav.writeframesraw(chunk)

print("Saved speech.wav")
```

For a live conversation, the [WebSocket endpoint](/v2/tts-websocket) is a
better fit than one request per sentence. You keep one connection for the
whole call, send text as your model writes it, and stop a reply with one
message when the caller interrupts.

## 4. Pipecat

If you build on Pipecat, use our integration. Install it with
`uv add pipecat-mirai` and add `MiraiTTSService` to your pipeline:

```python
import os
from pipecat_mirai import MiraiTTSService

tts = MiraiTTSService(
    api_key=os.environ["MIRA_API_KEY"],
    settings=MiraiTTSService.Settings(voice="ashu"),
)
```

It asks for audio at your pipeline's sample rate, stops the reply when the
caller interrupts, and keeps one connection open for the call. See
[Pipecat](/v2/pipecat) for the recommended phone setup.

Other frameworks with an OpenAI TTS integration can call the endpoint directly.
Point them at `https://sandbox.voice.miraiminds.co/v1` with model `mira-tts`
and `response_format="pcm"`. The audio is 48 kHz unless you ask for another
rate, and `X-Sample-Rate` always tells you which rate you got. On LiveKit
Agents, the OpenAI plugin needs one setting for that rate; see
[LiveKit](/v2/livekit).

## For phone calls

Four things keep a phone call's audio smooth.

### Ask for the line's format

Phone audio is 8 kHz. Request it from us and forward each chunk to your
provider as it arrives, base64-encoded into the provider's media message, with
no decoding or resampling on your side:

| Where the audio goes | `response_format` |
| :--- | :--- |
| Twilio Media Streams | `ulaw_8000` |
| Plivo audio streams | `ulaw_8000` |
| Exotel voice streaming | `pcm_8000` (16-bit PCM) |
| Your own SIP or RTP leg | `ulaw_8000` for PCMU, `alaw_8000` for PCMA, whichever codec the call negotiated |
| A wideband (16 kHz) leg | `pcm_16000` |

### Keep one connection open

Opening a new HTTPS connection for every sentence adds a TCP and TLS handshake
before that sentence can start: 0.4 to 1 second from India, and more when a
connection attempt has to be retried. Use the [WebSocket
endpoint](/v2/tts-websocket), which carries the whole call on one socket. If
you stay on HTTP, reuse one keep-alive client (one `httpx.AsyncClient` or
`requests.Session`) for every request in the call.

### Keep the provider 0.4 seconds ahead

If you send audio to the phone line at exactly real time, the provider holds
only the latest chunk, about 40 ms of audio. Any stall on your server longer
than that (a blocking call, a long JSON parse, many calls on one CPU) leaves
the line silent and the caller hears the voice break up. Send audio as it
arrives until the provider holds about 0.4 seconds more than the caller has
heard, then pace it. When the caller interrupts, tell the provider to drop what
it holds (Twilio `clear`, Plivo `clearAudio`, Exotel `clear`). The [phone
bridge example](/v2/tts-websocket#bridge-to-a-phone-call) shows the pattern for
Twilio. On Pipecat, pipecat-mirai (0.3.1 and later) does it for you
([recommended phone setup](/v2/pipecat#recommended-phone-setup)).

### Buffer the start of each sentence

Hold about 150 ms of audio before a sentence starts playing. Its first chunk
can be short and followed by a brief pause. If playback starts on it, the
caller hears a sliver of a word, a gap, then the rest.

### Why the format matters

Each stream needs its audio to arrive at least as fast as it plays. The
bandwidth one stream needs, before network overhead:

| Format | One stream | 12 streams |
| :--- | :--- | :--- |
| `pcm` at 48 kHz (the default) | 768 kbit/s | 9.2 Mbit/s |
| `pcm_24000` | 384 kbit/s | 4.6 Mbit/s |
| `pcm_16000` | 256 kbit/s | 3.1 Mbit/s |
| `pcm_8000` | 128 kbit/s | 1.5 Mbit/s |
| `ulaw_8000` or `alaw_8000` | 64 kbit/s | 0.8 Mbit/s |

At 48 kHz, six calls already need a steady 4.6 Mbit/s of download. On an
ordinary server link that can fall behind real time, and the calls start to
break up. 8 kHz μ-law needs a twelfth of that, and a narrowband phone line
carries no more than 8 kHz anyway.

With all four in place, using pipecat-mirai's `MiraiTTSService`, we ran 12 and
then 16 simultaneous phone calls through our API to the speech engine: 235 and
262 conversational turns, about a fifth of them interrupted by the caller.
Every call played with no audible gaps and no errors, and every sentence
arrived in order. We then repeated the 12-call run against this production
API from a client in Europe: 194 turns, again no gaps, no errors and every
sentence in order, with first audio at the phone (from the LLM's first token)
at 622 ms median and 737 ms at the 95th percentile. The [test
harness](https://github.com/MiraiMinds/pipecat-mirai/tree/main/benchmarks/customer-e2e)
is public, so you can run it yourself.

## Billing

{/* pricing:tts:start */}

**HTTP: ₹1.80 per 1,000 characters. WebSocket: ₹0.90 per minute connected.** Top-ups use the same rates.

On the text-to-speech WebSocket you pay for time, not text: every second the socket is open is billed at the per-minute rate, and the speech it carries is not charged again by the character. HTTP requests are billed by the character.

| Plan | Monthly commitment | Concurrent requests | Top-ups |
| --- | --- | --- | --- |
| Pay as you go | None | 5 | Top up anytime at the same rate: ₹1.80 / 1,000 characters |
| Business | ₹50,000 | 25 | Top up anytime at the same rate: ₹1.80 / 1,000 characters |

Shared endpoint. No contractual SLA. Monthly commitments are credited to your wallet. Unused credit never expires. All prices exclude GST.

**Enterprise:** Custom volume pricing, concurrency, dedicated endpoint and SLA. Top up anytime at the same rate.

{/* pricing:tts:end */}

Over HTTP, each request is rounded up to the paisa, and we charge only for
completed audio. If the engine fails, the stream stalls or your client
disconnects part-way, nothing is charged and no ledger row is written. The request still
appears in your log, with a status that says why. The output format, sample
rate, bitrate, speed, pitch and loudness do not change the price.

On the [WebSocket endpoint](/v2/tts-websocket#billing) you pay for the time
the socket is open, ₹0.90 a minute counted per second, and not for the
characters it speaks. Each full minute is one wallet row, and the last
part-minute is charged when the socket closes.

The charge is one debit row on the same [wallet](/v2/wallet) your calls draw
from, and it appears on the console billing statement under **Text to speech**:

```json title="GET /v2/wallet/transactions"
{
  "id": "txn_01K4N7Q2R5S8T4V7W9X1Y3ZB6C",
  "object": "wallet_transaction",
  "type": "debit",
  "amount_inr": 0.12,
  "balance_after_inr": 498.32,
  "call_id": null,
  "kind": "tts",
  "reference": "tts_01K4N7Q0V8ZR3M6D9F2H5J7K1P",
  "quantity": 62,
  "description": "Text to speech · 62 characters · shruti",
  "created_at": "2026-09-09T09:16:39Z"
}
```

| Field | Meaning |
| :--- | :--- |
| `kind` | `tts` here, `call` on call rows. Classify rows by this field, never by reading `description`. |
| `reference` | The `X-Request-Id` of the request that produced the audio. |
| `quantity` | Characters billed. This is the same number as `X-Chars-Billed`. |

If your wallet cannot cover the request, you get a `402` before anything is
synthesised. See [Wallet](/v2/wallet#list-transactions).

## Limits

| Limit | Default | Over the limit |
| :--- | :--- | :--- |
| Requests in flight | Your workspace's limit, **10** unless it has been set otherwise | `429 at_capacity` with a `Retry-After` header. |
| `input` length | **2,000 characters** | `400 invalid_request`. Split longer text. |
| Request rate | Per key (see [Limits](/v2/limits)) | `429 rate_limited` with a `Retry-After` header. |

We refuse an HTTP request over the limit instead of queueing it. Honour
`Retry-After` and send it again. A refused request does not hold a slot and
costs nothing. `at_capacity` can also come from a deployment-wide ceiling when
the speech node is saturated. Handle it the same way.

Sentences on the [WebSocket endpoint](/v2/tts-websocket) draw on the same
limit, but a sentence that finds it full waits up to 3 seconds for a slot
before it fails. A live conversation rides out a short burst there without a
retry loop of your own.

The limit is set per workspace, and a workspace starts at 10. The plans under
[Billing](#billing) list the concurrency each plan includes. If your
workspace's limit doesn't match your plan, or you need more, ask your Mirai
contact. Changing the limit is a provisioning change and needs no change to
your code.

## Your request log

We log every request, whether it completed, failed or was rejected, and you can
read the log yourself.

```bash
curl "https://sandbox.voice.miraiminds.co/v2/tts/requests?limit=50" \
  -H "Authorization: Bearer $MIRA_API_KEY"
```

```json title="200 OK"
{
  "id": "tts_01K4N7Q0V8ZR3M6D9F2H5J7K1P",
  "object": "tts_request",
  "created_at": "2026-09-09T09:16:39Z",
  "source": "api",
  "voice": "shruti",
  "model": "mira-tts",
  "format": "pcm",
  "chars": 62,
  "status": "completed",
  "cost_inr": 0.12,
  "first_byte_ms": 93,
  "total_ms": 3210,
  "bytes": 437760,
  "preview": "नमस्ते, मैं शालिनी बोल रही हूँ …",
  "error_code": null,
  "transport": "http"
}
```

Rows come newest first, and only from your own workspace:

| Query | Meaning |
| :--- | :--- |
| `limit` | Up to 200, default 50. |
| `cursor` | Opaque, from the response's `next_cursor`. |
| `from`, `to` | RFC3339 timestamps. |
| `status` | `completed`, `failed`, `truncated` or `rejected`. |
| `source` | `api` or `playground`. |

`GET /v2/tts/requests/{id}` returns a single row. The id is the
`X-Request-Id` you got back from the request.

| Field | Meaning |
| :--- | :--- |
| `status` | `completed` (audio relayed in full), `failed` (nothing usable), `truncated` (the stream stopped part-way), `rejected` (refused before synthesis because of a bad field, no balance or no free slot). |
| `source` | `api` for a request made with your key. `playground` for audio from the console's **Hear it** button. Playground requests are logged like any other but never charged, so `cost_inr` is `0`. |
| `transport` | `http` for a request to this endpoint, `websocket` for one sentence on a [streaming socket](/v2/tts-websocket). |
| `format` | What you were sent. `pcm` and `wav` mean 48 kHz. Any other format or rate carries its rate, for example `mulaw_8000`, `pcm_16000` or `wav_8000`. |
| `cost_inr` | What it cost. `0` unless `completed`. |
| `first_byte_ms` | Time to the first audio byte. In a live pipeline, this is the number to watch. |
| `total_ms`, `bytes` | Wall time and audio size for the whole request. |
| `error_code` | The `error.code` that was returned, or `null`. A sentence you cancelled on a socket reads `truncated` with `error_code` `cancelled`. |

<Note>
**We do not keep the text you send.** `preview` is the first 48 characters of
`input`, so a row is recognisable in a list. The rest is never stored.
</Note>

The same table is in the console under **Text to Speech → Logs**, if you would
rather check it there than poll the API.

## When something fails

| Status | `code` | Cause |
| :--- | :--- | :--- |
| 400 | `invalid_request` | Empty `input`, more than 2,000 characters, an unknown voice, an unsupported `response_format` or `sample_rate`, a `sample_rate` that conflicts with the rate in `response_format`, a `bitrate` on a format that has none or above what the codec carries at that sample rate, or a `speed`, `pitch` or `loudness` outside its range. The message names the valid values. |
| 401 | `unauthorized` | Missing or unknown key. Check the `Authorization: Bearer sk_live_…` header. |
| 402 | `insufficient_balance` | The wallet cannot cover this request. Nothing was synthesised and nothing was charged. |
| 404 | `model_not_found` | `model` is neither `mira-tts` nor the `mira-tts-v51` alias. |
| 429 | `at_capacity` | You already have as many requests in flight as your workspace allows (10 unless it has been set otherwise), or the deployment is saturated. Honour `Retry-After`. |
| 429 | `rate_limited` | Per-key request rate. Honour `Retry-After`, and see [Limits](/v2/limits). |
| 502 | `upstream_error` | The engine refused, returned no audio, or the stream stalled past its timeout. Nothing was charged; the message says which. Retry. |
| 503 | `fleet_offline` | No speech capacity is online. Nothing was charged. Honour `Retry-After`. |
| 503 | `format_unavailable` | You asked for `mp3`, `opus`, `aac` or `flac` and our server cannot encode it right now. Nothing was charged. Ask for `pcm` or `wav`, or retry later. |
| 503 | `maintenance_window` | Rare. Text to speech is down for planned maintenance. `Retry-After` counts the seconds until it is back. Nothing was charged. See [Availability](/v2/speech#availability). |

Errors use the same envelope as the rest of the API. See
[Errors](/v2/errors). If you are stuck on something this page does not cover,
reply on your onboarding thread, where a person reads it.

## Fixing choppy or broken audio

If callers hear gaps, clicks or a voice that breaks up, find the symptom below.

| What you hear | Likely cause | Fix |
| :--- | :--- | :--- |
| Fine on one call, breaking up once several calls run at once | 48 kHz PCM over a link that cannot carry every stream in real time | Ask for `ulaw_8000`, or the rate your player uses. See [Why the format matters](#why-the-format-matters). |
| A pause before some sentences, sometimes a second or more | A new HTTPS connection for each sentence | Keep one connection for the call: use the [WebSocket endpoint](/v2/tts-websocket), or one keep-alive HTTP client. |
| Short breaks in the middle of sentences, worse when your server is busy | Audio sent to the phone line at exactly real time, with nothing in hand when your server stalls | Keep the provider about 0.4 seconds ahead. See [For phone calls](#for-phone-calls). |
| A sliver of a word, a gap, then the rest of the sentence | Playback starts on the first, very short chunk | Hold about 150 ms of audio before each sentence starts playing. |
| A sentence goes missing under load, or you see `429 at_capacity` | More sentences in flight than your workspace limit (10 by default) | On the WebSocket, sentences wait up to 3 seconds for a slot. On HTTP, honour `Retry-After`. Ask us to raise the limit if you run many calls at once. |
| Static or noise, or a voice that is too fast, too slow or too high | The audio is decoded with the wrong encoding or rate | Read `X-Sample-Rate` and `X-Audio-Encoding` (on the WebSocket, `audio.start`) and set your player to match. |

To find out whether a gap starts on our side or yours, look the request up in
your [request log](#your-request-log). `first_byte_ms` is how long we took to
send the first audio, and `status` says whether all of it was delivered. If
those look normal and the caller still hears gaps, the audio is being held up
between our server and the caller: on your link, in your server's event loop,
or in how it is paced to the phone line. The fixes above cover each of those.

If you are on Pipecat, the [recommended phone setup](/v2/pipecat#recommended-phone-setup)
takes care of all of this except the size of your limit.
