A webhook subscription sends events to your HTTPS endpoint without a URL on every call.
You register an endpoint once, then pick the events it should receive:

- every call of one agent, or of the whole workspace, including inbound calls to your numbers and WhatsApp calls
- campaign lifecycle: started, paused, resumed, finished, stopped
- wallet alerts: balance low, calls refused for balance, balance back up
- payments: payment received, payment failed
- rented phone numbers: renewal coming up, renewed, released, purchase failed, and business verification updates
- do-not-call list: a number added or taken off
- status: incidents and planned maintenance that may affect your calls

A subscription can also [filter](#send-only-the-events-you-want) on what a call produced, so you get only the calls that matter, such as your leads. An endpoint can also be a list of email addresses instead of a URL, for the events a person acts on, including [one email per lead](#lead-emails). See [Send events by email](#send-events-by-email).

The per-call `webhook_url`, the campaign `webhook_url` and a phone number's `webhook_url` keep working as described in [Webhooks](/v2/webhooks).
If you use both for the same call or campaign with different URLs, both receive it. If a call's `webhook_url` is the same URL as a destination, that URL receives each event once, signed with the destination's secret. See [Which webhook secret do I use?](/v2/webhook-secrets)

<Tip>
In the console, open **Webhooks** to add an endpoint and tick events from a checklist. Everything on this page is the same feature through the API.
</Tip>

## Set it up

All routes use your API key and act on the key's workspace.

<Steps>
  <Step title="Create an endpoint">
    ```bash
    curl https://sandbox.voice.miraiminds.co/v2/webhooks/endpoints \
      -H "Authorization: Bearer sk_live_YOUR_API_KEY" \
      -H "Content-Type: application/json" \
      -H "Idempotency-Key: crm-endpoint-1" \
      -d '{"name": "CRM", "url": "https://crm.example.com/mirai/events"}'
    ```

    ```json Response (201)
    {
      "id": "whe_3f9c2a71d4b84e0f9a6b1c2d3e4f5a6b",
      "object": "webhook_endpoint",
      "name": "CRM",
      "url": "https://crm.example.com/mirai/events",
      "method": "POST",
      "header_names": [],
      "enabled": true,
      "revision": 1,
      "created_at": "2026-10-26T06:10:00Z",
      "signing_secret": "whsec_…",
      "signing_key_version": 1
    }
    ```

    <Warning>
    `signing_secret` is shown only in this response. Store it now. Reads never return it again.
    </Warning>

    The URL must be HTTPS on port 443. Optional `headers` (up to 16) are stored encrypted, and reads show only their names.
  </Step>
  <Step title="Subscribe it to events">
    ```bash
    curl https://sandbox.voice.miraiminds.co/v2/webhooks/subscriptions \
      -H "Authorization: Bearer sk_live_YOUR_API_KEY" \
      -H "Content-Type: application/json" \
      -d '{
        "endpoint_id": "whe_3f9c2a71d4b84e0f9a6b1c2d3e4f5a6b",
        "scope": {"type": "workspace"},
        "event_types": ["wallet.balance_low", "wallet.depleted", "campaign.completed", "call.completed"]
      }'
    ```

    For one agent only, use `"scope": {"type": "agent", "agent_id": "agt_…"}`. Wallet, payment, phone number, do-not-call and status events belong to the whole workspace, so an agent subscription cannot list them (the API answers `400`).
  </Step>
  <Step title="Send a test">
    ```bash
    curl https://sandbox.voice.miraiminds.co/v2/webhooks/endpoints/whe_3f9c2a71d4b84e0f9a6b1c2d3e4f5a6b/test \
      -H "Authorization: Bearer sk_live_YOUR_API_KEY" \
      -H "Content-Type: application/json" \
      -d '{"if_revision": 1, "event_type": "wallet.balance_low"}'
    ```

    This sends a real, signed request to your endpoint with made-up data and `"test": true`. The `202` response is the queued delivery. Look it up under [deliveries](#deliveries-and-retries).
  </Step>
</Steps>

`GET /v2/webhooks/event-types` lists every event with its label, group, one-line description, `scopes`, `email` (whether an email endpoint can take it), JSON schema and an example payload. It needs your API key.

## Send only the events you want

A subscription can carry `where`: conditions on what the event carries. Only events that match every condition are delivered. The rest create no delivery at all: nothing is queued, retried or counted as a failure.

```bash
curl https://sandbox.voice.miraiminds.co/v2/webhooks/subscriptions \
  -H "Authorization: Bearer sk_live_YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "endpoint_id": "whe_3f9c2a71d4b84e0f9a6b1c2d3e4f5a6b",
    "scope": {"type": "agent", "agent_id": "agt_…"},
    "event_types": ["call.analysis.completed"],
    "where": [{"field": "analysis.data.call_outcome", "in": ["callback_agreed", "call_later"]}]
  }'
```

Each condition has a `field` and an `in` list. The event matches when the value at `field` is one of the values in `in`.

| `field` | What it reads |
| :--- | :--- |
| `analysis.data.<field>` | One of your agent's [post-call result fields](/v2/analysis#turn-it-on), such as `analysis.data.call_outcome`. A nested field takes up to three names: `analysis.data.lead.score`. |
| `analysis.success` | The success verdict: `true`, `false` or `null`. |
| `analysis.outcome` | The agent's [outcome](/v2/analysis#outcomes), when it has a list of them. |
| `call.campaign_id` | The campaign that placed the call. |
| `call.direction` | `inbound` or `outbound`. |
| `call.channel`, `call.status`, `call.ended_reason` | As on the [call object](/v2/calls). |
| `call.metadata.<key>` | One key of the `metadata` you sent with the call. |

- `in` takes 1 to 50 strings, numbers, `true`, `false` or `null`. Strings match exactly.
- A field the event does not carry reads as `null`, so `"in": [null]` matches it.
- When the field holds a list, the event matches if any item in the list is one of the values.
- All conditions must hold. Up to 10 conditions; each field once.
- `analysis.*` reads the post-call result of `call.analysis.*` events, and the call's result on `call.processed` and `call.processing.completed`. Other call events don't carry a result, so a condition on `analysis.*` never matches them.
- On an agent subscription, a result field the agent's `output_schema` doesn't declare, or a value outside that field's `enum`, answers `400` with the fields or values it has. That catches a typo when you save, instead of a filter that never matches.
- `PATCH /v2/webhooks/subscriptions/{id}` with `where` replaces the filter, and `"where": []` removes it. A subscription without a filter has no `where` key.
- Test sends ignore filters: they always go.

## Event types

### Calls

Scope: one agent or the whole workspace.

| Event | When |
| :--- | :--- |
| `call.queued` | The call was accepted and is waiting to connect. |
| `call.started` | The call connected and the conversation began. |
| `call.completed` | The call ended normally. Analysis may still be running. |
| `call.failed` | No answer, busy, or a connection problem. |
| `call.aborted` | The call was cancelled before it finished. |
| `call.voicemail` | The call reached voicemail. |
| `call.recording.ready` | The recording is stored and can be downloaded. |
| `call.analysis.completed` / `.failed` / `.skipped` | Call analysis reached a final state. |
| `call.processed` | Analysis and post-call actions finished for this pass. |
| `call.processing.completed` | Recording, transcript, analysis and post-call actions have all finished, including failures. |
| `call.handoff.requested` | A [human takeover](/v2/handoff) was armed. We are ringing the person (`dial_out`), or they can dial in now (`dial_in`). |
| `call.handoff.started` | The person joined the call, and the agent stepped back. |
| `call.handoff.failed` | The takeover did not connect. `data.handoff.reason` is `no_answer`, `expired`, `join_failed`, `caller_left`, `dial_failed` or `worker_unsupported`. Unless the caller left, the caller is still with the agent. |
| `call.handoff.ended` | The person's part of the call is over, and the call ends with it. `data.handoff` has `duration_secs` and `ended_by`. |

`data.call` is the [call object](/v2/calls#the-call-object), the same object `GET /v2/calls/{id}` returns, on every call event. See [the call object in an event](/v2/webhooks#the-call-object-in-an-event). Takeover events also carry
`data.handoff`, the [handoff object](/v2/handoff#the-handoff-object). On a call
that had a takeover, `call.completed` and `call.processing.completed` carry
`data.call.handoffs`, `data.call.segments` and the split `cost`. See
[on the call](/v2/handoff#on-the-call).

### Campaigns

Scope: one agent (the campaigns that agent runs) or the whole workspace.

| Event | When |
| :--- | :--- |
| `campaign.started` | The campaign started calling. |
| `campaign.paused` | The campaign paused. `pause_reason` says why, for example `insufficient_balance`. |
| `campaign.resumed` | A paused campaign started calling again. |
| `campaign.completed` | The campaign called every contact it could and finished. |
| `campaign.stopped` | The campaign was stopped before it finished. |

`data.campaign` is the same object, with the same event `id`, that the campaign's own `webhook_url` receives.

### Wallet and payments

Scope: the whole workspace only.

| Event | When |
| :--- | :--- |
| `wallet.balance_low` | Your balance fell below your [alert level](#low-balance-alert-level). Sent once each time it crosses. |
| `wallet.depleted` | A call could not start, or a campaign paused, because the wallet cannot cover it. Sent once, then not again until the balance can cover such a call. |
| `wallet.balance_restored` | Your balance is back at or above the alert level after it was low. |
| `payment.succeeded` | A payment was received and credited. |
| `payment.failed` | An automatic debit or a plan renewal failed. |

The balance in these events is the one [`GET /v2/wallet`](/v2/wallet) shows: what you can spend, after calls in progress. We check it about once a minute, so `wallet.balance_low` reaches you within a minute of the crossing. A top-up, a call or an API charge can each cause one.

If several workspaces share your company's wallet, each workspace with a subscription receives the payment events.

### Phone numbers

Scope: the whole workspace only.

| Event | When |
| :--- | :--- |
| `phone_number.renewal_upcoming` | A number you rent from Mirai renews in 7 days, and again 24 hours before. Says whether your wallet covers the renewal, how much is missing, and whether it is already [reserved](/v2/phone-numbers#reserve-renewals-ahead-of-time). |
| `phone_number.renewed` | The renewal was paid from your wallet. The number keeps working for another term. |
| `phone_number.released` | The number was released and no longer takes calls: auto-renewal was off (`reason` `cancelled`) or the wallet could not cover the renewal (`reason` `insufficient_balance`). No renewal charge was made. |
| `phone_number.purchase_failed` | A number purchase did not complete. The amount held for it is back in your wallet. |
| `phone_number.verification_updated` | Your business verification for renting numbers changed state: `submitted`, `accepted`, `rejected` (with the reason), `suspended` or `expired`. `setup_state` `ready` means you can rent now. |

There is no grace period on a rented number: if the wallet cannot cover the renewal when it is due, the number is released. That is why the reminders come twice. The account's owners and billing members also get each of these moments by email (the two reminders, a receipt for each renewal, the release and a failed purchase), with or without a subscription. Pending verifications are checked in the background, so you do not need to poll [refresh](/v2/phone-numbers#rent-a-number-from-mirai).

`data.workspace_id` is the workspace that holds the number. For a [sub-workspace](/v2/sub-workspaces#phone-numbers-in-a-sub-workspace), the event goes to that sub-workspace's subscriptions and to your account's own, because your account's wallet pays. The two copies have different event `id`s and the same `data`. These events cannot go to an email endpoint.

### Spending limits

Scope: the whole workspace only.

| Event | When |
| :--- | :--- |
| `workspace.spend_limit.warning` | A sub-workspace's charges for ended calls reached 80% of its [spending limit](/v2/sub-workspaces#spending-limits). |
| `workspace.spend_limit.reached` | A sub-workspace's charges for ended calls reached 100% of its limit, or the first call was refused for the limit. |

Each is sent once per period for each limit setting: once a month on a monthly limit, once on a lifetime limit. Changing the limit's amount or period lets them fire again. The event goes to the sub-workspace's own subscriptions and to your account's, and both events can go to an [email endpoint](#send-events-by-email). The top-level `workspace_id` is the workspace receiving the copy. `data.workspace_id` always names the sub-workspace and `data.parent_id` your account.

### Do-not-call list

Scope: the whole workspace only.

| Event | When |
| :--- | :--- |
| `dnc.added` | A number was added to your [do-not-call list](/v2/dnc): by you (`POST /v2/dnc` or the console), because the person asked on a call not to be called again, or because they filed a complaint about one of your calls. |
| `dnc.removed` | A number was taken off it (`DELETE /v2/dnc/{phone}` or the console). Your calls can ring it again. |

Use them to put the person on your WhatsApp, SMS and email stop lists at the same moment. You get one `dnc.added` each time a number is added. Adding a number that is already on the list sends nothing, and a number added again after it was removed sends a new event. `data.source` says how the number got there. See the [payload](#payloads). These events go to HTTPS endpoints only.

### Status

Scope: the whole workspace only.

| Event | When |
| :--- | :--- |
| `incident.opened` | Part of the platform is down or degraded and may affect your calls. |
| `incident.updated` | News on an open incident: what we found, or a new state, impact or set of parts. |
| `incident.resolved` | The incident is over. A later note, such as the root cause, is another `incident.resolved`. |
| `maintenance.scheduled` | Planned maintenance was announced, or changed before it started. |
| `maintenance.started` | The maintenance is under way. |
| `maintenance.completed` | The maintenance is over. |

`data.incident` is the incident as the update left it, and `data.impact` is what it did to your workspace: your agents with failed calls, and whether those calls were charged. Incidents on the public status page reach every subscribed workspace. Others reach only the workspaces they affect. See [Status and incidents](/v2/status#webhook-events) for the payload and a receiver that tells your own customers.

Your account's owners also get these updates by email without any subscription. See [Status emails to owners](/v2/status#status-emails-to-owners).

## Send events by email

An endpoint can deliver to email addresses instead of a URL. Use one when a person should act on an event and you have no receiver to build: an incident, a low wallet, a stopped campaign.

```bash
curl https://sandbox.voice.miraiminds.co/v2/webhooks/endpoints \
  -H "Authorization: Bearer sk_live_YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "Ops inbox", "type": "email", "emails": ["ops@example.com", "oncall@example.com"]}'
```

```json Response (201)
{
  "id": "whe_8d41b0c2e97f4a6b8c3d2e1f0a9b8c7d",
  "object": "webhook_endpoint",
  "name": "Ops inbox",
  "type": "email",
  "emails": [
    {"address": "ops@example.com", "state": "confirmed", "confirmed_at": "2026-11-12T06:10:00Z"},
    {"address": "oncall@example.com", "state": "pending"}
  ],
  "header_names": [],
  "enabled": true,
  "revision": 1,
  "created_at": "2026-11-12T06:10:00Z"
}
```

Send `type: "email"` and `emails` (1 to 10 plain addresses, each once) instead of `url`. An email endpoint has no `url`, `method`, `headers` or signing secret, so the response has no `signing_secret` and `rotate-secret` answers `400`. Then [subscribe it](#set-it-up) like any other endpoint.

### Who gets the emails

Each address has a `state`:

- `confirmed`: it gets every event the endpoint is subscribed to. Someone on your team who has signed in to the console is confirmed as soon as you add them.
- `pending`: anyone else first gets one email asking them to confirm, and nothing more until they open the link and press **Confirm**. The link works for 7 days.

Once an address confirms, it is confirmed for every email endpoint in the workspace. To ask a pending address again, save the endpoint with `PATCH /v2/webhooks/endpoints/{id}` and its `emails`: we send a fresh link at most once a day per address. A workspace sends at most 20 confirmation emails a day.

### Which events can go by email

| Group | Events |
| :--- | :--- |
| Status | `incident.opened`, `incident.updated`, `incident.resolved`, `maintenance.scheduled`, `maintenance.started`, `maintenance.completed` |
| Wallet | `wallet.balance_low`, `wallet.depleted`, `wallet.balance_restored` |
| Payments | `payment.succeeded`, `payment.failed` |
| Spending limits | `workspace.spend_limit.warning`, `workspace.spend_limit.reached` |
| Campaigns | `campaign.paused`, `campaign.completed`, `campaign.stopped` |
| Post-call results | `call.analysis.completed`, only with a `where` filter on the result. See [Lead emails](#lead-emails). |

Every other call event, and recording, processing and do-not-call events, go to HTTPS endpoints only. A subscription or test that puts one of them on an email endpoint answers `400`, naming the event. In `GET /v2/webhooks/event-types`, each event says `"email": true` or `"email": false`.

### Lead emails

Your sales team can get an email for each lead without a webhook server. Subscribe an email endpoint to `call.analysis.completed` for one agent, with a filter on the result that makes a call a lead:

```bash
curl https://sandbox.voice.miraiminds.co/v2/webhooks/endpoints \
  -H "Authorization: Bearer sk_live_YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "Sales team", "type": "email", "emails": ["sales@example.com", "head.sales@example.com"]}'

curl https://sandbox.voice.miraiminds.co/v2/webhooks/subscriptions \
  -H "Authorization: Bearer sk_live_YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "endpoint_id": "whe_8d41b0c2e97f4a6b8c3d2e1f0a9b8c7d",
    "scope": {"type": "agent", "agent_id": "agt_…"},
    "event_types": ["call.analysis.completed"],
    "where": [{"field": "analysis.data.call_outcome", "in": ["callback_agreed", "call_later"]}]
  }'
```

Each matching call becomes one email, usually a minute or two after the call ends:

- The subject says the outcome, who it was and the campaign: `Callback agreed: Ravi Shah · Diwali leads`.
- Then the person's name (from the contact's `client_name`, `customer_name`, `contact_name`, `full_name`, `name`, `first_name` or `lead_name`, when the call came from a campaign) and number, the outcome, when to call back, every other result field the agent filled in, the campaign, the agent, when the call happened (in the campaign's time zone, India time otherwise) and how long it lasted.
- Your `summary` result field (or the analysis summary) is the first paragraph. The transcript is not included.
- A button opens the call in the console.

The rules:

- A `call.analysis.completed` subscription on an email endpoint needs a `where` condition on an `analysis.*` field. Without one, the API answers `400`: one email for every call is too many. To get every call, use an HTTPS endpoint.
- Each call is emailed once per endpoint. If the result is worked out again, or two subscriptions on the same endpoint match, the second delivery is `skipped` with `last_error: "already_emailed"`.
- An endpoint gets at most 500 lead emails a day (India time). After that, deliveries are `skipped` with `last_error: "daily_email_limit"`, and you can [retry](#deliveries-and-retries) them the next day.
- Only confirmed addresses get them, as with every email endpoint.
- A test of `call.analysis.completed` fills in the first value of each field your filter checks, so the test email looks like a real lead.

### Sending and receipts

- Each event becomes one email to each confirmed address. Addresses are read when the email is sent, so an address you remove stops getting mail at once, even for events already queued.
- A delivery's state is `sent` when our mail server accepted the message for every confirmed address. We can't see whether it then reached the inbox.
- A refused address fails the attempt with `smtp_error`. The [retry schedule](#deliveries-and-retries) then mails only the addresses still owed. An endpoint with no confirmed address fails with `no_confirmed_address`.
- A delivery is `skipped` when a lead email was not sent on purpose: the call was already emailed, or the endpoint reached its daily limit (see [Lead emails](#lead-emails)). `last_error` says which.
- Test sends are marked `[Test]` in the subject. Each email endpoint takes at most 5 tests in a rolling hour. The next one answers `429 rate_limited`.
- Email endpoints count toward the workspace's limit of 20 endpoints.

## Low balance alert level

The alert level is ₹500 until you change it.

```bash
curl -X PATCH https://sandbox.voice.miraiminds.co/v2/webhooks/settings \
  -H "Authorization: Bearer sk_live_YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"low_balance_threshold_inr": 2000}'
```

```json Response
{
  "object": "webhook_settings",
  "low_balance_threshold_inr": 2000,
  "status_email": true,
  "revision": 1,
  "updated_at": "2026-10-26T06:12:00Z"
}
```

`GET /v2/webhooks/settings` reads it, and also returns `call_webhook_urls`, the `webhook_url`s your calls used in the last 7 days ([details](/v2/webhook-secrets#read-per-call-deliveries-with-the-api)). Set it to `0` to turn `wallet.balance_low` off; `wallet.depleted` still fires. Pass `if_revision` if you want a stale write refused.

The same settings hold `status_email`, `true` until you change it. It controls the incident and maintenance emails your account's owners get without a subscription. Send `{"status_email": false}` to leave this workspace out of them ([details](/v2/status#status-emails-to-owners)). A `PATCH` can change either field, or both; a field you leave out keeps its value.

## Payloads

Every event has the same envelope.

| Field | Meaning |
| :--- | :--- |
| `id` | Unique event id. Deduplicate on it. |
| `type` | The event type. |
| `created_at` | When the event happened (RFC 3339, UTC). |
| `schema_version` | `2026-09-22`. |
| `workspace_id` | Your workspace. |
| `subject` | `{type, id}`: the call, campaign, wallet (your workspace id), payment, rental, verification, workspace (a sub-workspace's id), do-not-call entry (`dnc_entry`, the phone number) or incident the event is about. |
| `source_id` | What produced the event. Repeats of the same occurrence share it. |
| `test` | `true` for synthetic tests, test calls and test-mode payments. |
| `data` | The event's content. |

## Verify the signature

Every delivery to an HTTPS endpoint is signed with the endpoint's `signing_secret` (the Destination secret), using the same scheme as [call webhooks](/v2/webhooks#signature-verification). Email endpoints are not signed. A signed delivery carries these headers:

```http
X-Mirai-Signature: t=1785057398,v1=771bca27e1647dfbe59ff5d8f32d9de69be246f6e604c05bddcbaefd8604ccb3
X-Mirai-Delivery-ID: whd_…
X-Mirai-Attempt: 1
X-Mirai-Key-Version: 1
X-Mirai-Signed-With: whe_3f9c2a71d4b84e0f9a6b1c2d3e4f5a6b
```

`v1` is the lowercase hex `HMAC-SHA256(signing_secret, "<t>.<raw_body>")`. Reject a timestamp more than 300 seconds from now, and compare in constant time.

<CodeGroup>
```js Node.js
import crypto from "node:crypto";

export function verify(rawBody, header, secret) {
  const parts = Object.fromEntries(header.split(",").map((p) => p.split("=")));
  const t = Number(parts.t);
  if (!t || Math.abs(Date.now() / 1000 - t) > 300) return false;
  const expected = crypto.createHmac("sha256", secret).update(`${t}.`).update(rawBody).digest("hex");
  const given = Buffer.from(parts.v1 ?? "", "hex");
  const want = Buffer.from(expected, "hex");
  return given.length === want.length && crypto.timingSafeEqual(given, want);
}
```

```python Python
import hashlib, hmac, time

def verify(raw_body: bytes, header: str, secret: str) -> bool:
    parts = dict(p.split("=", 1) for p in header.split(","))
    t = int(parts.get("t", "0"))
    if not t or abs(time.time() - t) > 300:
        return False
    expected = hmac.new(secret.encode(), f"{t}.".encode() + raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, parts.get("v1", ""))
```
</CodeGroup>

Verify the raw bytes you received, before parsing the JSON. `X-Mirai-Signed-With` names the destination whose secret signed the delivery. If a check fails, see [A webhook failed its signature check](/v2/webhook-secrets#a-webhook-failed-its-signature-check).

**Rotating the secret.** `POST /v2/webhooks/endpoints/{id}/rotate-secret` with `{"if_revision": N}` returns a new secret that starts signing five minutes later. Install it alongside the old one before then, and keep the old one for an hour. `X-Mirai-Key-Version` tells you which secret signed a delivery.

## Deliveries and retries

Delivery is at least once. Return any `2xx` after you have stored the event; store `id` with a unique constraint so a repeat does nothing. Events can arrive out of order, so act on `created_at` and the object's state, not arrival order.

A failed delivery is retried after 1 second, 7 seconds, 49 seconds, about 6 minutes, then every 30 minutes, for up to 24 hours. A `Retry-After` header from you is respected.

| Route | Use |
| :--- | :--- |
| `GET /v2/webhooks/deliveries` | Delivery history. Filter by `endpoint_id`, `agent_id`, `call_id`, `event_type`, `status`, `from`, `to`. |
| `GET /v2/webhooks/deliveries/{id}/attempts` | Every attempt, with status code, error and latency. |
| `POST /v2/webhooks/deliveries/{id}/retry` | Send a `failed` or `skipped` delivery again with the same event id and bytes. Body: `{"if_revision": N}`. A skipped lead email is skipped again while its reason still holds. |
| `GET /v2/webhooks/events` | Every event from the last 30 days, including ones no subscription matched. |
| `GET /v2/webhooks/call-deliveries` | Attempts to deliver to the `webhook_url` passed on calls. See [per-call deliveries](/v2/webhook-secrets#read-per-call-deliveries-with-the-api). |

## Manage endpoints and subscriptions

| Route | Use |
| :--- | :--- |
| `GET /v2/webhooks/endpoints` | List endpoints with delivery health. |
| `PATCH /v2/webhooks/endpoints/{id}` | Change `name`, `url`, `headers` or `enabled` (`if_revision` required). On an email endpoint, send `emails` to replace the list. An endpoint never changes type. `enabled: false` pauses sending; queued deliveries wait. |
| `DELETE /v2/webhooks/endpoints/{id}?if_revision=N` | Remove an endpoint and its subscriptions. Unsent deliveries are cancelled. |
| `GET /v2/webhooks/subscriptions` | List subscriptions; filter by `endpoint_id` or `agent_id`. |
| `PATCH /v2/webhooks/subscriptions/{id}` | Change `event_types`, `where` or `enabled` (`if_revision` required). `"where": []` removes the filter. Endpoint and scope are fixed; create a new subscription to change them. |
| `DELETE /v2/webhooks/subscriptions/{id}?if_revision=N` | Stop future events. Deliveries already queued still go out. |

Creating an endpoint, rotating, testing and retrying accept an `Idempotency-Key` header, so a retried request never creates a second endpoint or secret. Two subscriptions that match the same event for the same endpoint produce one delivery.

## Checklist

- Endpoint is public HTTPS on port 443 and answers `2xx` within a few seconds.
- `signing_secret` stored; signature checked on the raw body; old timestamps rejected.
- Events stored by `id` with a unique constraint.
- Alert level set to the balance at which you want to top up.
- Status events going to an HTTPS or email endpoint that someone watches.
- A test event sent and seen in your logs.
