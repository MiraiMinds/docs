An **agent** is the reusable configuration a call runs: what it says first, how
it behaves, which voice, which language, and when it must stop. Calls reference
an agent by ID; per-call differences go in [`variables`](/v2/calls#variables).

An agent runs either one prompt (`system_prompt`) or a graph of steps (`flow`).
See [Node-based agents](/v2/node-agents) for the graph.

Base URL `https://sandbox.voice.miraiminds.co`. All endpoints require
`Authorization: Bearer sk_live_…`.

## Tools

Add `tools` to connect your APIs before, during, or after a call. On-call HTTP
tools can run synchronously or in the background, with the result returned to
the voice agent when ready. See [Tools](/v2/tools) for setup, conditions, secrets,
callbacks, and examples.

## Node-based agents

Add `flow` to run the conversation as a graph: nodes with their own
instructions, and transitions the model takes when their conditions are met.
With a flow, `system_prompt` and `first_message` are optional and unused, and
only `pre_call` and `post_call` tools are allowed. See
[Node-based agents](/v2/node-agents) for the schema and a worked example.

## The agent object

```json
{
  "id": "agt_01JZQ8F3K7M2N5P9R4T6V8W0XZ",
  "object": "agent",
  "name": "Order Confirmation",
  "system_prompt": "You are Priya from Acme. Confirm order {{order_id}} with {{customer_name}}…",
  "first_message": "नमस्ते {{customer_name}}, मैं Acme से Priya बोल रही हूँ।",
  "voice": { "voice_id": "ashu", "language": "hi-IN" },
  "language": "hi-IN",
  "max_duration_secs": 300,
  "end_call": {
    "enabled": true,
    "message": "धन्यवाद, आपका दिन शुभ हो।",
    "confirm": true
  },
  "voicemail": { "action": "hangup" },
  "background_sound": { "sound": "off" },
  "behavior": { "interruptions": "normal", "adaptive_interruptions": true },
  "created_at": "2026-07-26T09:14:02Z",
  "updated_at": "2026-07-26T09:14:02Z"
}
```

### Fields

| Field | Type | Required | Description |
| :--- | :--- | :--- | :--- |
| `name` | string | yes | Human label. Shown in logs and the console. |
| `system_prompt` | string | yes, unless `flow` is set | The agent's instructions. Supports `{{variable}}` placeholders. Unused on a node-based agent. |
| `first_message` | string | yes, unless `flow` is set | Spoken the moment the callee answers, before the model runs. Keep it short, because it sets your first-audio latency. Unused on a node-based agent: its start node's `greeting` opens the call. |
| `voice` | object | yes | See [Voice](#voice). |
| `language` | string | yes | BCP-47 conversation language, e.g. `hi-IN`, `en-IN`. Drives ASR and the model's default output language. |
| `max_duration_secs` | integer | no | Hard cap. When it is reached, the call ends with `ended_reason: exceeded-max-duration`. Minimum `30`, maximum `1800`, default `300`. |
| `tools` | array | no | Tool definitions for this agent. See [Tools](/v2/tools). PATCH replaces the full list. |
| `analysis` | object | no | What to work out after each call: a summary, a success verdict, extracted fields and the follow-up message to send. See [Analysis](#analysis). PATCH replaces the whole object. |
| `emit_processed_webhook` | boolean | no | Defaults to `true`. Set `false` to suppress `call.processed` while keeping analysis and post-call tools enabled. |
| `end_call` | object | no | See [Ending a call](#ending-a-call). |
| `voicemail` | object | no | See [Voicemail](#voicemail). |
| `background_sound` | string \| object | no | Room ambience under the agent's voice. See [Background sound](#background-sound). Default `off`. |
| `behavior` | object | no | How the agent takes turns with the caller. See [Behavior](#behavior). Default `{"interruptions": "normal", "adaptive_interruptions": true}`. |
| `flow` | object \| null | no | A node graph. Makes this a [node-based agent](/v2/node-agents). Present on the agent object only when set. PATCH replaces the whole graph; `null` removes it. |

Server-set and read-only: `id`, `object`, `created_at`, `updated_at`.

### Analysis

`analysis` reads each finished call once more, after the hangup, so it never
slows the conversation. Turn it on with `"enabled": true` and describe what you
want in `prompt`, `success_criteria` and `output_schema`. Add `templates` and
the agent also picks the message template to send next, such as a WhatsApp or
SMS template, and fills in its variables from the conversation. See
[Call analysis](/v2/analysis) for every field, the result and two worked
examples.

```json
{
  "analysis": {
    "enabled": true,
    "prompt": "Summarise the call in two sentences: what the customer wanted and what was agreed.",
    "success_criteria": "The customer confirmed the order or chose a payment method.",
    "templates": {
      "instructions": "Pick the WhatsApp message to send. Choose none if the customer declined.",
      "items": [
        {
          "name": "payment_link_hi",
          "language": "hi",
          "description": "Sends the payment link when the customer agreed to pay online.",
          "variables": [
            { "key": "1", "description": "Customer first name" },
            { "key": "2", "description": "Order amount in rupees, digits only" }
          ]
        }
      ]
    }
  }
}
```

### Calls from

`calls_from` sets the number the agent's outbound calls and campaigns ring from when they do not choose one. Send `{ "pool_id": "pool_…" }` for a [phone pool](/v2/phone-numbers), or `{ "phone_number_id": "phn_…" }` for one of your numbers, never both. `null` unsets it. See [phone numbers and pools](/v2/phone-numbers#which-number-a-call-comes-from) for the order a call's number is chosen in.

### Voice

```json
{ "voice": { "voice_id": "ashu", "language": "hi-IN" } }
```

| Field | Type | Description |
| :--- | :--- | :--- |
| `voice_id` | string | **Required.** A voice from the catalogue: `ashu`, `neha`, `shruti` or `sameer`. The same voices are available on every [tier](/general/tiers). Anything else returns a `400` that names the allowed set. See [Voices](/v2/voices). |
| `language` | string | Rendering language for that voice. Omit to inherit the agent's `language`. **Accepted and stored, not yet honoured.** See the note below. |

<Note>
**`voice.language` is recorded, not yet applied**

The field is validated, stored and echoed back, and it travels with the call
payload. Today, though, the voice renders in the agent's top-level `language`.
If you set both to the same value, you get what you expect. If you set them
differently, the top-level one wins until per-voice rendering ships.
</Note>

Listen to the catalogue and pick a `voice_id` in the
[console](https://sandbox.voice.miraiminds.co). See [Voices](/v2/voices).

### Ending a call

The agent gets an `end_call` tool. When it fires, the agent speaks `message` and
hangs up.

| Field | Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `enabled` | boolean | `true` | Set `false` to remove the tool entirely. The call then ends only when the callee hangs up or `max_duration_secs` is reached. |
| `message` | string | `""` | Spoken farewell, played **after** the agent's own goodbye when the call ends. It is empty by default, so the agent's last line is the farewell. Live today. |
| `confirm` | boolean | `true` | Require a second `end_call` within the confirmation window before hanging up. This stops fast models from ending the call on a bare "ok". |

If you define an explicit `end_call` entry in `tools`, that entry controls whether
the tool is available, including its condition. Its `builtin.enabled`,
`builtin.message`, and `builtin.confirm` settings override the corresponding
agent settings when supplied. See [Tools](/v2/tools).

<Tip>
Leave `confirm: true` unless you are running a one-turn notification. It costs
one extra turn in the rare case and prevents the far more expensive failure of
hanging up on a customer mid-sentence.
</Tip>

### Voicemail

```json
{
  "voicemail": {
    "action": "message",
    "message": "Hi, this is Acme calling about your order. We'll try again later."
  }
}
```

| Field | Type | Description |
| :--- | :--- | :--- |
| `action` | `hangup` \| `message` | What to do when an answering machine is detected. Default `hangup`. |
| `message` | string | Required when `action` is `message`. Spoken once, then the call ends. |

Either way the call ends with `status: voicemail` and fires a
[`call.voicemail`](/v2/webhooks#call-voicemail) event. Voicemail detection is
available on every tier. See [tiers](/general/tiers#one-stack-on-every-tier).

### Background sound

An agent speaking out of complete silence is the most obvious sign that nobody
is there. `background_sound` plays room ambience under the voice for the whole
call.

```json
{ "background_sound": "office" }
```

Or, with the level:

```json
{ "background_sound": { "sound": "office", "volume": 0.2 } }
```

| Field | Type | Description |
| :--- | :--- | :--- |
| `sound` | `off` \| `office` | Which room. Default `off`. |
| `volume` | number | `0` to `1`, default `0.08`. The default sits about 22 dB under the agent's voice, so you notice the room when the line goes quiet but it never competes with the words. Raise it if you want the room more present. A bed at `0.3` is already at conversation level. |

Before you turn it on, note two things:

- The bed is in the call recording too, because it is what the callee heard.
  If you run your own transcription over recordings, test it first.
- It does not touch what the agent hears. Ambience is mixed into the outbound
  audio only, so your callers' speech recognition is unchanged.

### Behavior

`behavior` decides how easily the caller can cut the agent off while it is
speaking. You can also set it in the console: **Agent Studio → Behavior**.

```json
{ "behavior": { "interruptions": "firm", "adaptive_interruptions": true } }
```

| Field | Type | Description |
| :--- | :--- | :--- |
| `interruptions` | `easy` \| `normal` \| `firm` \| `never` | How much the caller has to say before the agent stops talking. Default `normal`. |
| `adaptive_interruptions` | boolean | Default `true`. The agent learns how loud the caller is from their own turns. While the agent is speaking, a voice much quieter than theirs, such as someone else in the room, cannot interrupt it, and its words are not passed to the agent. If an interruption turns out to be nothing, the agent repeats the line it was cut off on. |

| `interruptions` | The agent stops when the caller says |
| :--- | :--- |
| `easy` | One word, or about half a second of speech. |
| `normal` | Two words, or about 0.7 seconds of speech. |
| `firm` | Three words, or about 1.2 seconds of speech. |
| `never` | Nothing. The agent always finishes its line, then answers what the caller said. |

Acknowledgements such as "haan", "ji" and "ok" never interrupt. A clear stop
word such as "stop" or "ruko" interrupts at every setting except `never`.

On a [node-based agent](/v2/node-agents), a node with `allow_interrupt: false`
is never interrupted whatever this setting is, and `never` applies to every node.

`PATCH` merges `behavior` field by field: the fields you send change and the
others keep their values, unlike other nested objects, which are replaced
whole. Send `"behavior": null` to go back to the defaults. The setting takes
effect on the next call and is saved with each agent revision.

<Tip>
If your callers use a laptop's built-in microphone in a busy room, keep
`adaptive_interruptions` on and let the browser reduce noise. See
[Microphone capture](/v2/web-calls#microphone-capture).
</Tip>

## Create an agent

```http
POST /v2/agents
```

<Tabs>
  <Tab title="cURL">
    ```bash
    curl -X POST https://sandbox.voice.miraiminds.co/v2/agents \
      -H "Authorization: Bearer sk_live_YOUR_API_KEY" \

      -d '{
        "name": "Order Confirmation",
        "system_prompt": "You are Priya from Acme. Confirm order {{order_id}} with {{customer_name}}.",
        "first_message": "नमस्ते {{customer_name}}, मैं Acme से Priya बोल रही हूँ।",
        "voice": { "voice_id": "ashu", "language": "hi-IN" },
        "language": "hi-IN",
        "max_duration_secs": 300,
        "end_call": { "enabled": true, "message": "धन्यवाद, आपका दिन शुभ हो।", "confirm": true },
        "voicemail": { "action": "hangup" }

    ```
  </Tab>

    ```python
        f"{API}/v2/agents",

            "system_prompt": "You are Priya from Acme. Confirm order {{order_id}} with {{customer_name}}.",
            "first_message": "नमस्ते {{customer_name}}, मैं Acme से Priya बोल रही हूँ।",

    ```
  </Tab>
  <Tab title="Node.js">
    ```javascript

    const res = await fetch(`${API}/v2/agents`, {
      method: "POST",
      headers: { ...auth, "Content-Type": "application/json" },
      body: JSON.stringify({
        name: "Order Confirmation",
        system_prompt: "You are Priya from Acme. Confirm order {{order_id}} with {{customer_name}}.",
        first_message: "नमस्ते {{customer_name}}, मैं Acme से Priya बोल रही हूँ।",
        voice: { voice_id: "ashu", language: "hi-IN" },
        language: "hi-IN",

      }),
    });
    if (!res.ok) throw new Error(JSON.stringify(await res.json()));
    const agent = await res.json();
    ```
  </Tab>
</Tabs>

Responds with **`201 Created`** and the full [agent object](#the-agent-object).

| Error | `error.code` | Cause |
| :--- | :--- | :--- |
| `400` | `invalid_request` | Missing required field, unknown `voice_id`, `max_duration_secs` out of range |
| `400` | `invalid_flow` | A problem in `flow`, or an `on_call` tool on a node-based agent. The body lists every problem with its path; see [errors](/v2/node-agents#errors). |
| `401` | `unauthorized` | Bad or missing key |

## Update an agent

```http
PATCH /v2/agents/{id}
```

Send only the fields you are changing. Nested objects such as `voice`,
`end_call`, `voicemail`, `background_sound`, `analysis` and `tools` are replaced wholesale,
so to change `end_call.message`, send the whole `end_call` object. `behavior`
is the one exception: it is merged field by field, as described in
[Behavior](#behavior). `flow` is replaced wholesale too: send the whole graph,
or use [`PUT /v2/agents/{id}/flow`](/v2/node-agents#edit-the-graph).
`"flow": null` turns a node-based agent back into a single-prompt agent.

<Tabs>
  <Tab title="cURL">
    ```bash
    curl -X PATCH https://sandbox.voice.miraiminds.co/v2/agents/agt_01JZQ8F3K7M2N5P9R4T6V8W0XZ \
      -H "Authorization: Bearer sk_live_YOUR_API_KEY" \
      -H "Content-Type: application/json" \
      -d '{ "max_duration_secs": 180, "voice": { "voice_id": "neha", "language": "hi-IN" } }'
    ```
  </Tab>
  <Tab title="Python">
    ```python
    agent = httpx.patch(
        f"{API}/v2/agents/agt_01JZQ8F3K7M2N5P9R4T6V8W0XZ",
        headers=auth,
        json={"max_duration_secs": 180, "voice": {"voice_id": "neha", "language": "hi-IN"}},
        timeout=30,
    ).raise_for_status().json()
    ```
  </Tab>
  <Tab title="Node.js">
    ```javascript
    const agent = await fetch(
      `${API}/v2/agents/agt_01JZQ8F3K7M2N5P9R4T6V8W0XZ`,
      {
        method: "PATCH",
        headers: { ...auth, "Content-Type": "application/json" },
        body: JSON.stringify({
          max_duration_secs: 180,
          voice: { voice_id: "neha", language: "hi-IN" },
        }),
      }
    ).then((r) => r.json());
    ```
  </Tab>
</Tabs>

Responds with **`200 OK`** and the updated agent object.

<Warning>
An update takes effect on the **next** call. Calls already `queued`, `dialing`
or `in_progress` keep the configuration they were created with.
</Warning>

## Delete an agent

```http
DELETE /v2/agents/{id}
```

```bash
curl -X DELETE https://sandbox.voice.miraiminds.co/v2/agents/agt_01JZQ8F3K7M2N5P9R4T6V8W0XZ \
  -H "Authorization: Bearer sk_live_YOUR_API_KEY"
```

**`204 No Content`**.

The delete is soft: the agent stops appearing in `GET /v2/agents` and can no
longer be used for new calls, but historical calls keep resolving their
`agent_id`. Calls already in flight are not affected.

## Read an agent's logs

```http
GET /v2/agents/{id}/logs?part=&level=&call_id=&name=&since=&until=&limit=&cursor=
```

Everything that happened on this agent's calls, newest first. One row per
event: a tool run, a tool the model asked for that the agent doesn't have, the
variables a call received, the post-call analysis, and each call starting and
ending. It's the same list the console shows in Agent Studio under **Logs**, so
you can debug from code or from the console and see the same rows.

| Query param | Description |
| :--- | :--- |
| `part` | Optional. One of `prompt`, `tools`, `variables`, `results`, `calls`. Leave it out for every part. |
| `level` | Optional. `error`, `warning` or `info`. `errors`, `warnings` and `all` also work. |
| `call_id` | Optional. Only this call's rows. |
| `name` | Optional. Only rows about one tool, variable or result field. `calls` rows have no name, so a named query never returns them. |
| `since`, `until` | Optional. RFC 3339 bounds on the row time. `until` defaults to now and `since` to 7 days before `until`. They can be at most 90 days apart. Escape a `+` offset as `%2B`. |
| `limit` | Optional. 1–200, default 50. |
| `cursor` | Optional. The `next_cursor` from the previous page. |

```bash
curl -G https://sandbox.voice.miraiminds.co/v2/agents/agt_01JZQ8F3K7M2N5P9R4T6V8W0XZ/logs \
  -H "Authorization: Bearer sk_live_YOUR_API_KEY" \
  --data-urlencode "level=error" \
  --data-urlencode "limit=20"
```


| Field | Type | Description |
| :--- | :--- | :--- |
| `ts` | string | When it happened, in UTC. |
| `call_id` | string | The call it happened on. Open it with [`GET /v2/calls/{id}`](/v2/calls#get-a-call). |
| `part` | string | The part of the agent it's about: `prompt`, `tools`, `variables`, `results` or `calls`. |
| `level` | string | `error`, `warning` or `info`. |
| `event` | string | What happened. See the table below. |
| `name` | string | The tool, variable or result field it's about. Empty on `calls` rows. |
| `summary` | string | One line that says what happened, so you rarely need `detail`. |
| `detail` | object | The full record. Its fields depend on `event`. |

| `part` | `event` | Levels |
| :--- | :--- | :--- |
| `tools` | `tool_run` | `info` when the tool ran, was skipped by its condition, is turned off, or the call ended while it ran. `error` for anything else: a timeout, an HTTP error, a failed transform. |
| `prompt` | `tool_missing` | `warning`. The model asked for a tool this agent doesn't have. The call carried on without it. Usually the prompt names a tool you haven't added. |
| `variables` | `received` | `info`. The variables a call started with, after defaults. |
| `results` | `analysis_done`, `analysis_failed` | `info` when the analysis finished. `warning` when it finished but took more than 10 seconds to arrive. `error` when it failed. |
| `calls` | `created`, `ended` | `ended` is `info` for a normal ending, `warning` when the caller never spoke, and `error` when the call failed for a technical reason. |

Page with `next_cursor` until `has_more` is `false`. See
[pagination](/v2/overview#pagination).

A `variables` row's `detail` holds the values the call received, such as a
customer's name or order number. Treat logs like the call data they come from,
and keep your API key on your server.

<Note>
Rows about variables and results start from calls made on 14 October 2026.
Rows about tools the model asked for but the agent doesn't have start from
15 October 2026.
</Note>

## Writing a good prompt

A single-prompt agent does one job, start to finish, usually in under two or
three minutes. The [prompting guide](/v2/prompting-guide) covers this in
detail. In short:

- **Name the job in the first line.** "Confirm order `{{order_id}}`. Nothing else."
- **Cap reply length explicitly.** "One or two short sentences." Long turns are
  the single biggest driver of perceived latency.
- **State the ending condition.** "When the customer confirms or refuses, thank
  them and call `end_call`." Without this the model keeps talking.
- **Put per-call data in `variables`, not the prompt.** One agent can then run
  thousands of calls without being re-created.
- **Write in the language you will speak.** A Hindi call driven by an English
  prompt code-switches badly. Write the Hindi lines in Devanagari.

Prompts that cause trouble: multi-branch scripts ("if they say X, then go
through the following seven questions"), which belong in a
[node-based agent](/v2/node-agents); instructions that assume the model
remembers a previous call; and data the agent must fetch mid-call, which is a
job for an on-call [tool](/v2/tools).
